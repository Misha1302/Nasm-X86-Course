## За 30 секунд

- Поле объекта лежит по постоянному смещению от адреса объекта.
- Метод получает адрес объекта через скрытый параметр `this`.
- Объект с виртуальными методами обычно содержит указатель `vptr` на таблицу виртуальных функций.
- Виртуальный вызов состоит из двух разных действий: выбрать адрес функции и передать объект как `this` согласно ABI.
- Один косвенный `call` без контекста не доказывает виртуальность.
- Точное расположение объекта и место передачи `this` зависят от ABI и компилятора.

## Зачем этот день

В исходном коде C++ мы видим классы, поля и методы:

```cpp
obj.field
obj.method()
obj.virtualMethod()
```

Процессор видит только память, адреса и вызовы функций. Поэтому на низком уровне:

```text
объект              = область памяти с полями
обычный метод       = функция со скрытым параметром this
виртуальный метод   = функция, адрес которой выбирается из таблицы
полный вызов метода = передача this + выбор/задание адреса функции + call
```

Эта модель помогает читать листинги. Но она не доказывает точный исходный код: похожую схему может создавать и обычная таблица указателей на функции.

## Главная мысль

Обычный объект похож на структуру. Например:

```cpp
struct Point {
    int x;
    int y;
};
```

При типичном расположении IA-32:

```text
адрес объекта + 0  -> x
адрес объекта + 4  -> y
```

Имена `x` и `y` в памяти не хранятся. Компилятор заранее заменяет их смещениями.

Центральный инвариант:

> Чтобы нестатический метод мог обращаться к полям, непосредственно перед входом в метод адрес нужного объекта должен быть передан как `this` по правилам выбранного ABI; выбор адреса функции из таблицы сам по себе этого не обеспечивает.

---

## 1. Обычный метод и скрытый `this`

Метод:

```cpp
int Point::sum() {
    return x + y;
}
```

можно мысленно представить как обычную функцию:

```cpp
int Point_sum(Point* this) {
    return this->x + this->y;
}
```

В листинге это может выглядеть так:

```asm
; ecx условно содержит this
mov eax, [ecx]
add eax, [ecx + 4]
ret
```

Подтверждённые факты:

- один адрес используется как основа;
- читаются два 32-битных значения по смещениям `0` и `4`;
- сумма возвращается через `eax`.

Гипотеза: адрес в `ecx` — это `this`, а два значения — поля объекта. Для уверенного вывода нужен контекст ABI и вызова.

---

## 2. Где передаётся `this`

Место передачи `this` зависит от ABI и компилятора. В 32-битном коде можно встретить `thiscall`, где `this` передаётся через `ecx`. В другом соглашении тот же адрес может лежать в стеке как скрытый аргумент.

Поэтому формулируй вывод осторожно:

```text
Факт: ecx используется как указатель на область памяти.
Гипотеза при известном thiscall-контексте: ecx содержит this.
```

Не называй гипотезу доказанным фактом только из-за знакомого шаблона.

Если выбран стековый контракт, полный вызов обязан отдельно доказать порядок аргументов, padding и cleanup. Нельзя смешивать этот вариант с `thiscall` в одном фрагменте без явного перехода между ABI-моделями.

---

## 3. Виртуальные методы и `vptr`

Рассмотрим класс:

```cpp
struct Base {
    virtual int f();
    int x;
};
```

Объекту нужен способ выбрать реализацию `f`. Обычно в объект добавляется служебный указатель `vptr`:

```text
Объект Base:

+------------------+
| vptr             | ----+
+------------------+     |
| x                |     |
+------------------+     |
                         v
                  +------------------+
                  | адрес Base::f    |
                  +------------------+
                  | адрес другого    |
                  | виртуального     |
                  | метода           |
                  +------------------+
```

Таблица виртуальных функций хранится отдельно. Сам объект хранит только указатель на неё и обычные поля.

---

## 4. Разрешение цели и полный виртуальный вызов

Исходный код:

```cpp
Base* p = ...;
p->f();
```

Сначала отделим **выбор адреса функции** от передачи объекта.

### Только разрешение адреса цели

```asm
mov eax, [p]          ; eax = адрес объекта
mov edx, [eax]        ; edx = возможный vptr
mov edx, [edx]        ; edx = адрес функции из первой ячейки
```

После этого `edx` содержит возможную цель вызова, но метод ещё не вызван и контракт `this` ещё не доказан.

### Полный вызов в условной IA-32 thiscall-модели

Если в выбранной модели `this` передаётся через `ecx`, один возможный законченный фрагмент:

```asm
mov ecx, [p]          ; ecx = адрес объекта, возможный this
mov eax, [ecx]        ; eax = возможный vptr
call dword [eax]      ; цель из первой ячейки; ecx всё ещё передаёт объект
```

Если метод находится в следующей 4-байтной ячейке:

```asm
call dword [eax + 4]
```

Здесь разные регистры имеют разные роли:

```text
ecx → адрес объекта для вызываемого метода;
eax → адрес возможной таблицы;
[eax+offset] → адрес вызываемой функции.
```

Неверный неполный шаблон:

```asm
mov eax, [p]
mov edx, [eax]
call dword [edx]
```

Он может выбрать функцию из таблицы, но сам по себе не показывает, где вызываемый метод получит адрес объекта. Если ABI требует `this` в `ecx`, этот фрагмент обязан сначала сохранить объект в `ecx`.

### Стековый вариант

В другой ABI-модели адрес объекта может передаваться скрытым стековым аргументом. Тогда перед `call` должен существовать явный аргумент `this`, а область вызова обязана удовлетворять правилам выбранного соглашения. Конкретный padding нельзя вывести без исходного состояния `esp` и полного списка аргументов.

Курс не объявляет один из этих вариантов универсальным. Его цель — научить проверять два независимых обязательства:

1. откуда взят адрес функции;
2. как вызываемая функция получает адрес объекта.

Главное отличие:

| Вызов | Откуда берётся адрес функции | Что ещё требуется |
|---|---|---|
| прямой | записан в самой инструкции `call` | передать обычные и скрытые аргументы по ABI |
| косвенный | прочитан из регистра или памяти | передать обычные и скрытые аргументы по ABI |
| возможный виртуальный | обычно прочитан из таблицы объекта | передать тот же объект как `this` по ABI |

Любой виртуальный вызов является косвенным, но не любой косвенный вызов является виртуальным.

## 5. Наследование

Простой случай:

```cpp
struct Base {
    int a;
};

struct Derived : Base {
    int b;
};
```

Объект `Derived` может начинаться с базовой части:

```text
+------------------+
| Base::a          |
+------------------+
| Derived::b       |
+------------------+
```

При множественном или виртуальном наследовании расположение сложнее. Кроме смещений полей, компилятор может корректировать адрес `this` перед вызовом конкретной реализации. В этом курсе достаточно помнить: значение `this` и адрес функции являются отдельными частями контракта.

---

::: info Обзорная тема
Для ядра главы обязательны скрытый `this`, смещения полей, `vptr`, таблица виртуальных функций, разрешение цели и полный виртуальный вызов. RTTI рассматривается только на уровне узнавания.
:::

## 6. RTTI

RTTI — служебные сведения о типах во время выполнения. Они нужны, например, для `dynamic_cast` и `typeid`.

Для курса достаточно понимать:

```text
RTTI — это данные, созданные компилятором, а не магия языка.
```

Точное устройство RTTI зависит от ABI.

---

## 7. Как читать подозрительный листинг

Фрагмент:

```asm
mov eax, [ecx]
call dword [eax + 8]
```

Подтверждает только следующее:

1. `ecx` используется как указатель;
2. по адресу `[ecx]` читается ещё один указатель;
3. адрес вызываемой функции читается по смещению `8`;
4. вызов является косвенным;
5. значение `ecx` не перезаписано этим фрагментом и поэтому доступно вызываемой функции, но его роль требует ABI-контекста.

Возможная интерпретация при известной thiscall-модели:

```text
ecx      = this
[ecx]    = vptr
[eax+8]  = ячейка таблицы виртуальных функций
```

Но ту же машинную схему может дать таблица обратных вызовов. Поэтому в ответе разделяй факты и гипотезы.

Фрагмент, который загружает объект в `eax`, затем использует `eax` только для получения таблицы и нигде не передаёт объект согласно известному ABI, является поводом искать потерянный `this`, а не автоматически объявлять вызов корректным.

---

## 8. Что где хранится

| Понятие C++ | Низкоуровневое представление |
|---|---|
| поле | байты по постоянному смещению |
| объект | область памяти с полями |
| обычный метод | функция со скрытым параметром `this` |
| виртуальный метод | функция, адрес которой выбирается из таблицы |
| `this` | указатель на текущий объект, переданный по ABI |
| виртуальная цель | адрес функции из предполагаемой таблицы |
| полный вызов | корректные аргументы, `this`, адрес цели и `call` |
| наследование | базовая часть, дополнительные поля и иногда корректировка `this` |
| RTTI | служебные сведения о типах |
| имя метода | обычно не хранится в каждом объекте |

## Практика

#### 1. Нарисуй возможное расположение объекта

```cpp
struct A {
    virtual void f();
    int x;
    int y;
};
```

<details>
<summary>Ответ</summary>

Один из типичных вариантов:

```text
+------------------+
| vptr             |
+------------------+
| x                |
+------------------+
| y                |
+------------------+
```

Точное расположение зависит от ABI.

</details>

#### 2. Что такое скрытый `this`?

<details>
<summary>Ответ</summary>

Это адрес объекта, для которого вызван метод. Он должен быть передан вызываемой функции способом, заданным ABI.

</details>

#### 3. Чем виртуальный вызов отличается от прямого?

<details>
<summary>Ответ</summary>

При прямом вызове адрес функции записан в инструкции. При возможном виртуальном вызове адрес обычно читается из таблицы объекта. Оба варианта всё равно обязаны передать `this` и остальные аргументы по ABI.

</details>

#### 4. Хранятся ли методы внутри каждого объекта?

<details>
<summary>Ответ</summary>

Нет. Код методов хранится отдельно. Объект содержит поля и, возможно, служебные указатели.

</details>

#### 5. Что может означать `mov eax, [ecx+4]` внутри метода?

<details>
<summary>Ответ</summary>

Чтение 32-битного поля по смещению `4`, если `ecx` содержит адрес объекта.

</details>

#### 6. Отдели факт от гипотезы

```asm
mov eax, [ecx]
call dword [eax+8]
```

Назови подтверждённые факты, возможную C++-интерпретацию и ABI-условие полного вызова.

<details>
<summary>Ответ</summary>

Факты: `ecx` разыменовывается; адрес вызова читается из памяти по смещению `8`; вызов косвенный. Гипотеза: `ecx` содержит `this`, `[ecx]` — `vptr`, а `[eax+8]` — ячейка таблицы. Полный вызов доказан только при известном контракте, в котором нужный адрес объекта действительно передаётся через `ecx`.

</details>

#### 7. Найди потерянный `this`

Для условной модели «`this` находится в `ecx`» исправь:

```asm
mov eax, [p]
mov edx, [eax]
call dword [edx]
```

<details>
<summary>Ответ</summary>

Один возможный вариант:

```asm
mov ecx, [p]
mov eax, [ecx]
call dword [eax]
```

Теперь `ecx` сохраняет адрес объекта для вызываемого метода, а `eax` используется для разрешения цели.

</details>

#### 8. Только адрес или полный вызов?

```asm
mov eax, [p]
mov edx, [eax]
mov edx, [edx+4]
```

<details>
<summary>Ответ</summary>

Это только возможное разрешение адреса функции. Нет `call`, а способ передачи `this` не показан.

</details>

## Типовые ошибки

| Ошибка | Почему неверно |
|---|---|
| считать, что объект хранит копии методов | код методов хранится отдельно |
| считать `vptr` обычным полем исходного класса | это служебная деталь реализации |
| выбирать адрес функции и забывать передать `this` | вызываемый метод не получает адрес нужного объекта |
| считать наличие `call [table]` полным ABI-контрактом | цель и аргументы являются разными обязательствами |
| называть любой косвенный вызов виртуальным | это может быть обычная таблица указателей на функции |
| переносить расположение и место `this` между ABI без проверки | смещения, регистры и стековые правила могут отличаться |
| выдавать гипотезу за факт | листинг часто допускает несколько исходных представлений |
