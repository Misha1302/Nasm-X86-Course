# День 01. Что вообще происходит, когда программа запускается

## Опора на материалы ВШЭ

`Slides2026-00 - intro.pdf`, `Slides2026-01.pdf`: зачем курс связывает C, ассемблер, архитектуру, производительность, отладку и безопасность.

## Зачем этот день

Ты уже умеешь писать C++. Например:

```cpp
int x = 2;
int y = 3;
int z = x + y;
```

Для тебя это одна понятная строка: “сложить `x` и `y`, положить в `z`”.

Но процессор не видит “переменные C++” и не понимает выражение целиком. Он выполняет маленькие команды: прочитать значение, положить в регистр, сложить, записать, перейти по адресу.

Сегодня не нужно писать сложный NASM. Задача дня — понять, **где ассемблер находится между C++ и железом**.

---

## Главная мысль

C++ — удобный язык для человека.

Ассемблер — почти прямой текстовый вид команд процессора.

Машинный код — байты, которые CPU реально исполняет.

```text
C++ source
   |
   | compiler
   v
Assembly source
   |
   | assembler
   v
Object file (.o)
   |
   | linker
   v
Executable
   |
   | OS loader
   v
Process in memory
   |
   | CPU executes machine instructions
   v
Result
```

Можно думать так:

```text
C++ говорит:       что хотим посчитать.
Assembly говорит:  какими командами это сделать.
Machine code:      как эти команды закодированы байтами.
CPU:               просто выполняет байты.
```

---

## Почему ассемблер вообще нужен

Не для того, чтобы все программы писать вручную. Это почти всегда плохая идея.

Ассемблер нужен, чтобы видеть нижний уровень:

- где реально лежат данные;
- почему происходит переполнение;
- что значит “адрес”;
- как работает вызов функции;
- почему выход за границы массива опасен;
- что делает компилятор;
- как читать дизассемблирование на экзамене или в отладке.

Хорошая формулировка:

> Ассемблер — это способ перестать гадать, что делает машина.

---

## Где asm реально используется

Если очень абстрактно, ассемблер нужен в трёх случаях:

| Причина | Что это значит |
|---|---|
| Привязка к архитектуре | нужна конкретная инструкция конкретного процессора |
| Производительность | нужно ускорить очень горячий участок |
| Полный контроль | нужно управлять регистрами, стеком, ABI, адресами |

Более конкретно:

- операционные системы, драйверы, загрузчики;
- компиляторы, интерпретаторы, JIT;
- runtime-библиотеки языков;
- libc и низкоуровневые функции памяти/строк;
- кодеки, криптография, обработка изображений;
- HFT и low-latency системы;
- reverse engineering и security;
- embedded и микроконтроллеры.

Но важно не романтизировать:

> Обычно на asm пишут не всю программу, а маленькие критические куски.

Современный компилятор часто генерирует очень хороший код. Хороший low-level программист сначала измеряет, смотрит дизассемблирование, понимает bottleneck, и только потом решает, нужен ли ручной asm.

---

## Аккуратные примеры для рассказа

Эти примеры можно использовать, но публично лучше проверять точные факты под текущую версию проекта.

| Пример | Как говорить аккуратно |
|---|---|
| FFmpeg | В медиабиблиотеках часто есть архитектурно-зависимые SIMD/asm-оптимизации в горячих местах. Не надо говорить, что “весь FFmpeg на asm”. |
| KolibriOS | Есть маленькие ОС, где ассемблер используется очень широко; KolibriOS/FASM часто приводят как пример. Размер и формулировку лучше проверить. |
| .NET Runtime | В рантаймах языков есть платформенно-зависимые низкоуровневые куски: startup, interop, atomics, helpers, memory routines. Конкретные утверждения про строки лучше проверять. |
| libc | Реализации libc могут иметь оптимизированные версии `memcpy`, `memmove`, `strlen` и похожих функций под конкретные архитектуры. |

Правильный стиль: не “я слышал байку”, а “в таких проектах действительно бывают архитектурно-зависимые оптимизации; конкретику проверяем”.

---

## Первый мостик: C++ → машинные шаги

C++:

```cpp
z = x + y;
```

Процессор не решает это выражение “целиком”. Ему нужно что-то вроде:

```asm
mov eax, [x]    ; взять x из памяти в регистр eax
add eax, [y]    ; прибавить y к eax
mov [z], eax    ; записать результат обратно в память
```

Пока не надо глубоко понимать квадратные скобки. Это будет в дне 05.

Сейчас важно ощущение:

```text
C++ expression
   |
   v
load data -> compute in register -> store result
```

То есть выражение распадается на маленькие шаги.

---

## Почему процессор не знает `while`

В C++:

```cpp
while (x > 0) {
    x--;
}
```

А на низком уровне это идея:

```text
.loop:
    проверить x > 0
    если нет — уйти в .end
    уменьшить x
    прыгнуть обратно в .loop
.end:
```

То есть `while` — это удобная форма для человека. Для процессора это сравнение, условный переход и безусловный переход.

В этом курсе почти всё будет раскладываться так:

| C++ | Низкоуровневая идея |
|---|---|
| переменная | значение в памяти или регистре |
| выражение | последовательность маленьких операций |
| `if` | сравнение + условный переход |
| `while` | метка + проверка + переход назад |
| функция | `call`, стек, `ret` |
| массив | базовый адрес + индекс * размер элемента |

---

## Почему мы пока не берём x64

x64 важен, но для первых недель он будет мешать.

В x64:

- больше регистров;
- другие имена: `rax`, `rbx`, `rcx`, ...;
- аргументы часто передаются через регистры;
- соглашение вызова зависит от ОС;
- стек всё ещё важен, но выглядит иначе.

А курс и задачи сейчас про `nasm-x86`, то есть IA-32:

```text
eax, ebx, ecx, edx
esp, ebp
stack arguments
cdecl
```

Поэтому договор простой:

> x64 существует, но пока не смешиваем две модели в голове.

# День 02. SASM, терминал и сборка без магии

## Опора на материалы ВШЭ

`Slides2026-04.pdf`: SASM, Linux x86/Ubuntu-лаборатория, базовая программа NASM.

## Зачем этот день

SASM удобен: написал код, нажал Run, получил результат.

Но если сборка сломалась, одной кнопки уже мало. Нужно понимать, что происходит под капотом:

```text
.asm -> .o -> executable -> process
```

Сегодня мы снимаем магию с кнопки Run и учимся собирать программу руками из терминала Linux.

---

## Главная мысль

Файл `.asm` сам не запускается.

Сначала его собирает NASM в object file. Потом linker собирает executable. Потом ОС загружает executable в память и запускает процесс.

```text
main.asm
   |
   | nasm -f elf32
   v
main.o
   |
   | gcc -m32 -no-pie
   v
main
   |
   | ./main
   v
output
```

SASM обычно делает эти шаги за тебя. Мы хотим понимать их вручную.

---

## Минимальная NASM-программа

Создай файл `main.asm`:

```asm
section .text
global main

main:
    xor eax, eax
    ret
```

Что здесь происходит:

| Строка | Смысл |
|---|---|
| `section .text` | дальше идёт код |
| `global main` | метка `main` видна линкеру |
| `main:` | начало функции `main` |
| `xor eax, eax` | сделать `eax = 0` |
| `ret` | вернуться из функции |

Почему `xor eax, eax`, а не `mov eax, 0`?

Оба варианта дают ноль, но `xor reg, reg` — частый короткий идиоматический способ обнуления регистра. В этом курсе ты будешь видеть его постоянно.

---

## Сборка из терминала

Команды:

```bash
nasm -f elf32 main.asm -o main.o
gcc -m32 -no-pie main.o -o main
./main
echo $?
```

Разберём каждую.

### `nasm -f elf32 main.asm -o main.o`

NASM читает текстовый asm и делает object file.

```text
main.asm  ->  main.o
```

`-f elf32` значит: создать 32-битный ELF object file. Это важно, потому что мы работаем с IA-32.

### `gcc -m32 -no-pie main.o -o main`

`gcc` здесь используется как удобный linker driver.

Он:

- вызывает линковщик;
- подключает стартовый код C runtime;
- подключает libc, если нужны `printf`, `scanf` и т.п.;
- делает итоговый executable.

`-m32` говорит: линковать как 32-битную программу.

## Важное уточнение: `-no-pie`

Почему не просто `gcc -m32 main.o -o main`?

Многие современные Linux-дистрибутивы по умолчанию собирают PIE-executable: position-independent executable.

А первые NASM-программы курса используют простые абсолютные адреса меток:

```asm
push fmtOut
mov eax, [x]
jmp [.table + 4*eax]
```

Для такого учебного IA-32 кода проще и честнее собирать без PIE:

```bash
gcc -m32 -no-pie main.o -o main
```

PIE, GOT, PLT и position-independent code — отдельная тема. Мы её упомянем позже, но не будем мешать в первые задачи.

---

### `./main`

Запуск программы.

### `echo $?`

Показать код возврата последней программы.

Наша программа возвращает `0`, потому что перед `ret` мы сделали:

```asm
xor eax, eax
```

В C это примерно как:

```cpp
return 0;
```

---

## Что такое `.asm`, `.o`, executable

| Файл | Что это |
|---|---|
| `main.asm` | текст на ассемблере |
| `main.o` | object file: машинный код и данные, но ещё не финальная программа |
| `main` | executable: файл, который ОС может загрузить и запустить |

Object file часто содержит:

- машинный код;
- данные;
- таблицы символов;
- relocation-записи;
- ссылки на внешние функции.

То есть `.o` уже не текст, но ещё не полноценная программа.

---

## Почему не просто `ld`

Можно линковать напрямую через `ld`, но для начала это лишняя боль. Когда в программе есть `main`, `printf`, `scanf`, стартовый код и libc, проще использовать:

```bash
gcc -m32 -no-pie main.o -o main
```

`gcc` сам правильно подставит нужные системные куски.

Для учебного курса это нормально: мы изучаем ассемблер, а не мучаемся с низкоуровневой линковкой в первый же день.

---

## `objdump`: смотрим внутрь

Когда программа собралась, полезно посмотреть, что внутри.

```bash
objdump -d -M intel main
```

- `-d` — дизассемблировать код;
- `-M intel` — показывать Intel-синтаксис, похожий на NASM.

Можно увидеть не только твой `main`, но и служебный код вокруг него. Это нормально.

Посмотреть секции:

```bash
objdump -h main
```

Посмотреть содержимое `.data`:

```bash
objdump -s -j .data main
```

---

## Что делает SASM

Когда ты нажимаешь Run в SASM, он примерно делает то же самое:

```text
SASM Run
   |
   v
save .asm
   |
   v
nasm
   |
   v
linker / gcc
   |
   v
run executable
   |
   v
show output
```

То есть SASM — не отдельный язык. Это удобная оболочка вокруг NASM, линковщика и запуска.

---

## Частая боль: нет 32-битных библиотек

Если `gcc -m32` ругается, часто проблема не в твоём asm, а в системе: не хватает 32-битных библиотек.

Ubuntu/Debian:

```bash
sudo apt install nasm gcc gcc-multilib libc6-dev-i386
```

Fedora:

```bash
sudo dnf install nasm gcc glibc-devel.i686 libgcc.i686
```

Если после установки всё равно не собирается, сначала проверь простую C-программу:

```c
int main() { return 0; }
```

Сборка:

```bash
gcc -m32 test.c -o test
```

Если даже это падает — проблема точно в окружении, а не в NASM-коде.

## Мини-практика: первая программа

Сделай файл `main.asm`, собери и запусти:

```asm
section .text
global main

main:
    mov eax, 7
    ret
```

Потом:

```bash
nasm -f elf32 main.asm -o main.o
gcc -m32 -no-pie main.o -o main
./main
echo $?
```

Ожидаемый код возврата:

```text
7
```

Почему? Потому что значение в `eax` считается возвращаемым значением `main`.

Важно: код возврата процесса обычно должен быть маленьким неотрицательным числом. Для больших вычислений так выводить результат не надо — позже будем использовать `printf`.

</details>

# День 03. Процессор как тупая, но очень быстрая машина

## Опора на материалы ВШЭ

`Slides2026-02.pdf`, `Slides2026-03.pdf`: цикл работы ЭВМ, операнды, инструкции, effective address.

## Зачем этот день

Перед тем как писать NASM, нужно договориться о модели мира.

В C++ ты думаешь примерно так:

```cpp
int x = a + b * 2;
```

А процессор не видит “выражение”. Он видит очень простые команды и выполняет их одну за другой.

Сегодня мы разбираем три главные вещи:

1. где процессор хранит временные значения;
2. откуда он берёт данные;
3. из чего состоит инструкция.

---

## Главная мысль

Инструкция — это операция плюс операнды.

Операнд может быть:

- регистром;
- памятью;
- константой прямо внутри инструкции.

```text
+---------------- CPU ----------------+
|                                      |
|  registers: eax ebx ecx edx ...     |
|  eip: address of next instruction    |
|  eflags: flags after operations      |
|  ALU: arithmetic and logic           |
|                                      |
+------------------|------------------+
                   |
                   v
+---------------- RAM ----------------+
| code | data | heap | stack | ...    |
+--------------------------------------+
```

Самая простая картина:

```text
memory  <->  registers  <->  ALU
```

Данные часто лежат в памяти, но считать удобно в регистрах.

---

## Процессор не “понимает программу”

Он делает цикл:

```text
fetch   -> взять байты инструкции по адресу eip
decode  -> понять, какая это инструкция
execute -> выполнить действие
write   -> записать результат
next    -> перейти к следующей инструкции
```

Упрощённо:

```text
eip указывает на инструкцию
CPU читает инструкцию
CPU выполняет её
eip переходит дальше
```

Позже мы увидим, что `jmp`, `call`, `ret` и условные переходы меняют этот обычный порядок.

---

## Что такое регистр

Регистр — это маленькая быстрая ячейка внутри процессора.

Можно думать так:

```text
память  = огромная тетрадь;
регистр = маленький листочек прямо в руках у процессора.
```

Пример:

```asm
mov eax, 10
add eax, 5
```

После этого:

```text
eax = 15
```

Мы не ходили в память. Всё было в регистре.

---

## Виды операндов

| Вид операнда | Пример | Как думать |
|---|---|---|
| register | `eax` | значение внутри CPU |
| memory | `[ebp-4]` | значение в RAM по адресу |
| immediate | `0xff` | число прямо в инструкции |

Разберём строки:

```asm
mov eax, ecx              ; register <- register
mov ecx, dword [0x2019]   ; register <- memory
mov dword [ebp-4], ebx    ; memory <- register
add eax, 0xff             ; register += immediate
```

### `mov eax, ecx`

```text
eax = ecx
```

Значение копируется из одного регистра в другой.

### `mov ecx, dword [0x2019]`

```text
ecx = memory[0x2019..0x201C]
```

`dword` говорит, что читаем 4 байта.

### `mov dword [ebp-4], ebx`

```text
memory[ebp-4] = ebx
```

Это запись в память.

### `add eax, 0xff`

```text
eax = eax + 0xff
```

Первый операнд меняется.

---

## Важное правило порядка операндов

В NASM обычно порядок такой:

```asm
instruction destination, source
```

То есть:

```asm
mov eax, ebx    ; eax = ebx
add eax, ebx    ; eax = eax + ebx
sub eax, 10     ; eax = eax - 10
```

Это не универсальная истина для всех ассемблерных синтаксисов. Например, AT&T-синтаксис пишет иначе. Но в этом курсе мы используем NASM/Intel-style, поэтому держим в голове именно это.

---

## `mov` копирует, а не переносит

Название `mov` слегка обманывает. Оно звучит как “переместить”, но на самом деле это копирование.

```asm
mov eax, ebx
```

После этой команды:

```text
eax получил значение ebx
ebx остался прежним
```

C++-аналогия:

```cpp
eax = ebx;
```

А не:

```cpp
eax = ebx;
ebx = 0;
```

---

## Почему нельзя память-память

В x86 многие инструкции не позволяют напрямую делать:

```asm
mov [a], [b] ; плохо / нельзя в таком виде
```

Обычно нужно через регистр:

```asm
mov eax, [b]
mov [a], eax
```

Это хороший стиль мышления:

```text
память -> регистр -> память
```

Регистры — рабочее место процессора.

---

## Мини-разбор C++ выражения

C++:

```cpp
x = a + b * 2;
```

Псевдо-NASM:

```asm
mov eax, [b]    ; eax = b
imul eax, 2     ; eax = b * 2
add eax, [a]    ; eax = a + b * 2
mov [x], eax    ; x = eax
```

Обрати внимание: мы не считаем всё выражение “одной магией”. Мы выбираем временный регистр и делаем шаги.

---

## Что такое `eip`

`eip` — instruction pointer. Он хранит адрес следующей инструкции.

Обычно после инструкции `eip` просто двигается дальше.

```text
instruction 1  <- eip
instruction 2
instruction 3
```

После выполнения первой:

```text
instruction 1
instruction 2  <- eip
instruction 3
```

Но переходы меняют `eip` не “на следующую”, а на заданную метку.

```asm
jmp .loop
```

Это значит: следующая инструкция будет не та, что лежит ниже, а та, что находится по адресу `.loop`.

---

## Что такое `eflags`

`eflags` — набор флагов, которые описывают результат некоторых операций.

Например:

```asm
sub eax, eax
```

Результат стал ноль. Значит, включится `ZF` — zero flag.

Пока не надо знать все флаги. Просто запомни:

```text
операции могут оставлять после себя “следы” во флагах;
условные переходы потом смотрят на эти следы.
```

Подробно разберём это в днях 11–12.

---

## Мини-челленджи

### 1. Destination и source

В строке:

```asm
add eax, ebx
```

кто destination, кто source?

<details>
<summary>Ответ</summary>

Destination — `eax`. Source — `ebx`. Результат записывается в `eax`.

</details>

### 2. Перевод в C++

Переведи:

```asm
mov eax, [a]
sub eax, 5
mov [b], eax
```

<details>
<summary>Ответ</summary>

Примерный C++-смысл:

```cpp
b = a - 5;
```

</details>

### 3. Почему не `mov [a], [b]`?

Объясни идею.

<details>
<summary>Ответ</summary>

Многие x86-инструкции не работают напрямую память-память. Нужно загрузить значение из памяти в регистр, а потом записать из регистра в память.

</details>

### 4. Что делает `mov`?

Выбери правильное:

```text
A. переносит значение и очищает источник
B. копирует значение
```

<details>
<summary>Ответ</summary>

B. `mov` копирует значение. Источник не очищается.

</details>

## Типовые ошибки

| Ошибка | Почему плохо |
|---|---|
| читать `add eax, ebx` как “просто сумма” | результат пишется в `eax` |
| думать, что `mov` очищает источник | `mov` копирует |
| путать регистр и память | `eax` и `[eax]` — разные вещи |
| забывать размер памяти | иногда нужен `byte`, `word`, `dword` |
| пытаться делать всё память-память | часто нужен промежуточный регистр |

# День 04. Почему `eax`, `ax`, `ah`, `al` — это не четыре переменные

## Опора на материалы ВШЭ

`Slides2026-02.pdf`: регистры IA-32, вложенность регистров и размеры операндов.

## Зачем этот день

В C++ ты обычно думаешь так: одна переменная — одно имя.

```cpp
int x;
char c;
```

В x86 всё чуть хитрее. Один и тот же физический регистр может иметь несколько имён для разных частей.

Самый важный пример:

```text
eax, ax, ah, al
```

Это не четыре независимые переменные. Это части одного регистра.

Если это не понять, потом будут странные ошибки в задачах с байтами, вводом, сдвигами и `movsx/movzx`.

---

## Главная мысль

`eax`, `ax`, `ah`, `al` перекрываются.

```text
31                              16 15       8 7        0
+--------------------------------+----------+----------+
|          high 16 bits          |    AH    |    AL    |
+--------------------------------+----------+----------+
                                  \__________ _________/
                                             |
                                             AX

EAX = full 32-bit register
AX  = low 16 bits of EAX
AH  = high byte of AX
AL  = low byte of AX
```

То есть:

```text
EAX содержит AX,
AX содержит AH и AL.
```

Если меняешь `AL`, меняется младший байт `EAX`.

---

## Пример руками

Пусть:

```text
eax = 0x12345678
```

Тогда:

```text
eax = 0x12345678
ax  =     0x5678
ah  =       0x56
al  =       0x78
```

Почему?

`AX` — младшие 16 бит `EAX`, то есть `0x5678`.

`AH` — старший байт `AX`, то есть `0x56`.

`AL` — младший байт `AX`, то есть `0x78`.

Теперь команда:

```asm
mov al, 0
```

Она меняет только младший байт.

Результат:

```text
eax = 0x12345600
```

Не `0`. Не `0x00000000`. Только младший байт стал нулём.

---

## Ещё один пример

Пусть:

```text
eax = 0xDEADBEEF
```

Тогда:

```text
ax = 0xBEEF
ah = 0xBE
al = 0xEF
```

Если выполнить:

```asm
mov ah, 0x11
```

то `ax` станет:

```text
0x11EF
```

а `eax` станет:

```text
0xDEAD11EF
```

Потому что `ah` — это байт на позициях 8..15.

---

## Основные регистры IA-32

В курсе чаще всего будут встречаться эти регистры:

| Register | Как о нём думать в этом курсе |
|---|---|
| `eax` | результат, аккумулятор, return value функции |
| `ebx` | обычный рабочий регистр; в CDECL функция должна его сохранять |
| `ecx` | счётчик; для переменных сдвигов используется `cl` |
| `edx` | старшая часть `edx:eax`; остаток после деления |
| `esi` | source/index register, часто указатель или индекс |
| `edi` | destination/index register, часто указатель или индекс |
| `esp` | stack pointer, вершина стека |
| `ebp` | frame pointer, база фрейма функции |
| `eip` | instruction pointer, адрес следующей инструкции |
| `eflags` | флаги результата |

Пока не надо запоминать исторические названия вроде accumulator/base/count/data глубоко. Но полезно знать интуицию:

```text
eax -> часто результат;
ecx -> часто счётчик;
edx -> часто деление;
esp/ebp -> стек и функции.
```

---

## Почему для сдвига нужен `cl`

В x86 команды сдвига могут брать количество сдвига из `cl`, то есть младшего байта `ecx`.

```asm
mov cl, 8
shl eax, cl
```

Не из всего `ecx`, а именно из `cl`.

Поэтому `ecx` часто всплывает в задачах со сдвигами и циклами.

---

## Размеры операндов

Ассемблеру часто нужно знать, сколько байтов ты хочешь читать или писать.

| Размер | Биты | Байты | Похоже на C/C++ |
|---|---:|---:|---|
| `byte` | 8 | 1 | `char`, `uint8_t` |
| `word` | 16 | 2 | `short`, `uint16_t` |
| `dword` | 32 | 4 | `int`, `uint32_t`, pointer в IA-32 |
| `qword` | 64 | 8 | `long long`, `double` |

Примеры:

```asm
mov al, byte [x]      ; прочитать 1 байт
mov ax, word [x]      ; прочитать 2 байта
mov eax, dword [x]    ; прочитать 4 байта
```

Иногда NASM сам понимает размер по регистру:

```asm
mov eax, [x] ; раз eax 32-битный, читаем dword
```

Но иногда размер нужно указать явно:

```asm
inc dword [x]
```

Потому что из `[x]` непонятно: увеличить байт, слово или двойное слово?

---

## Биты одинаковые, смысл разный

Регистр хранит биты. Он сам по себе не знает, signed это или unsigned.

```text
0xFFFFFFFF
```

Можно прочитать как:

```text
unsigned: 4294967295
signed:   -1
```

Это важно: типы C++ — это интерпретация. На уровне регистра лежит просто набор битов.

Позже это объяснит, почему есть разные переходы `jl` и `jb`, но нет отдельной команды `iadd`.

---

## Мини-челленджи

### 1. Разобрать `DEADBEEF`

Для:

```text
eax = 0xDEADBEEF
```

найди `ax`, `ah`, `al`.

<details>
<summary>Ответ</summary>

```text
ax = 0xBEEF
ah = 0xBE
al = 0xEF
```

</details>

### 2. Изменение `al`

Что будет с `eax`, если:

```text

```

и выполнить:

```asm

```

<details>
<summary>Ответ</summary>

```text

```

Поменялся только младший байт.

</details>

### 3. Изменение `ah`

Что будет после:

```text
eax = 0xAABBCCDD

```

<details>
<summary>Ответ</summary>

```text

```

</details>

### 4. Какой размер?

Какой размер у `dword`?

<details>

</details>

## Типовые ошибки

| Ошибка | Почему плохо |
|---|---|
| считать `eax` и `al` независимыми | `al` — часть `eax` |
| забыть, что `ah` тоже меняет `eax` | `ah` — байт внутри `ax` |
| путать `word` и `dword` | `word` = 16 бит, `dword` = 32 бит |
| думать, что регистр знает signed/unsigned | регистр хранит только биты |
| бездумно смешивать размеры | NASM может не собрать или получится не то |

# День 05. `x` и `[x]`: адрес против значения

## Опора на материалы ВШЭ

`Slides2026-02.pdf`, `Slides2026-04.pdf`: память, little-endian, секции `.data`, `.bss`, `.text`, статические данные и обращение к памяти.

## За 30 секунд

- `x` — адрес метки `x`.
- `[x]` — значение в памяти по адресу `x`.
- `mov eax, x` кладёт в `eax` адрес.
- `mov eax, [x]` читает значение.
- `mov [x], eax` записывает значение.
- `scanf` получает адрес: `push x`.
- `printf` получает значение: `push dword [x]`.

## Минимум после главы

Ты должен уметь:

- объяснить разницу между `x` и `[x]`;
- правильно вызвать `scanf("%d", &x)`;
- правильно вызвать `printf("%d", x)`;
- прочитать и записать `dword` в память;
- объяснить little-endian на числе `0x12345678`.

Можно пока не заучивать:

- `.got`, `.plt`, `.symtab`, `.strtab`;
- детали relocation;
- ELF-секции глубже `.text`, `.data`, `.bss`, `.rodata`.

---

## Главное правило

| NASM | C-похожий смысл | Что происходит |
|---|---|---|
| `x` | `&x` | адрес переменной |
| `[x]` | `x` | значение переменной |
| `mov eax, x` | `eax = &x` | адрес в регистр |
| `mov eax, [x]` | `eax = x` | значение в регистр |
| `mov [x], eax` | `x = eax` | запись в память |

Короткая привычка:

```text
видишь квадратные скобки -> идём в память по адресу
```

---

## Картинка памяти

```asm
section .data
    x dd 123
```

```text
address x
   |
   v
+----------------+
| 123            |
+----------------+
```

Теперь команды:

```asm
mov eax, x      ; eax = address of x
mov eax, [x]    ; eax = 123
mov [x], eax    ; memory[x] = eax
```

---

## Память как массив байтов

Можно думать так:

```cpp
uint8_t memory[...];
```

Адрес — это номер байта.

Если храним `dword`, он занимает 4 соседних байта.

---

## Секции NASM

| Секция | Что лежит |
|---|---|
| `.text` | код |
| `.data` | инициализированные изменяемые данные |
| `.bss` | зарезервированная зануленная память |
| `.rodata` | read-only constants, строки формата |

Пример:

```asm
section .data
    a dd 10
    b dd 20
    fmt db "%d", 10, 0

section .bss
    result resd 1
```

`a` и `b` уже имеют значения. `result` — место под будущий `dword`.

---

## Директивы данных

| Директива | Смысл | Пример |
|---|---|---|
| `db` | define byte | `c db 10` |
| `dw` | define word, 2 байта | `s dw 1000` |
| `dd` | define dword, 4 байта | `x dd 123` |
| `dq` | define qword, 8 байт | `q dq 123456` |
| `resb` | reserve bytes | `buf resb 64` |
| `resw` | reserve words | `arr resw 10` |
| `resd` | reserve dwords | `arr resd 10` |
| `resq` | reserve qwords | `arr resq 10` |

---

## Little-endian

IA-32 хранит многобайтовые числа в little-endian: младший байт лежит по младшему адресу.

```asm
section .data
x dd 0x12345678
```

В памяти:

```text
Address:   x      x+1    x+2    x+3
         +------+------+------+------+
Byte:    |  78  |  56  |  34  |  12  |
         +------+------+------+------+
```

Важно: little-endian — это порядок байтов в памяти, а не порядок цифр в записи числа.

---

## `scanf`: нужен адрес

C:

```c
scanf("%d", &x);
```

NASM:

```asm
push x
push fmtIn
call scanf
add esp, 8
```

Почему `x`?

Потому что `scanf` должен знать, куда записать число.

Плохо:

```asm
push dword [x]
```

`[x]` — старое значение переменной. Это не адрес для записи.

---

## `printf`: нужно значение

C:

```c
printf("%d", x);
```

NASM:

```asm
push dword [x]
push fmtOut
call printf
add esp, 8
```

Почему `[x]`?

Потому что `printf` должен напечатать значение.

Плохо:

```asm
push x
```

Так ты напечатаешь адрес, а не число.

---

## Размер памяти: зачем `dword`

Иногда NASM понимает размер по регистру:

```asm
mov eax, [x]     ; eax 32-bit, читаем dword
```

Но иногда размер не очевиден:

```asm
inc [x]          ; byte? word? dword?
```

Нужно явно:

```asm
inc dword [x]
```

---

## Полный пример

```asm
section .data
    fmtOut db "%d", 10, 0
    x dd 123

section .text
    extern printf
    global main

main:
    push dword [x]
    push fmtOut
    call printf
    add esp, 8

    xor eax, eax
    ret
```

Что важно:

| Строка | Смысл |
|---|---|
| `push dword [x]` | положить значение `123` |
| `push fmtOut` | положить адрес строки формата |

---

## Частые ошибки

| Ошибка | Почему плохо | Как правильно |
|---|---|---|
| `push [x]` для `scanf` | передаёшь значение вместо адреса | `push x` |
| `push x` для `printf("%d")` | печатаешь адрес вместо значения | `push dword [x]` |
| `push [fmtOut]` | передаёшь первые 4 байта строки как адрес | `push fmtOut` |
| думать, что `[x]` — адрес | наоборот: это значение по адресу | `x` — адрес, `[x]` — значение |
| забыть little-endian | неправильно читаешь байты в памяти | младший байт лежит первым |
| не указать `dword` там, где размер неясен | NASM не знает размер операции | `inc dword [x]` |

---

<details>
<summary>Ответ</summary>

# День 06. `scanf`, `printf` и первая настоящая программа

## Опора на материалы ВШЭ

## За 30 секунд

- `scanf` получает адрес, потому что записывает значение.
- `printf` получает значение, потому что печатает его.
- В IA-32 CDECL аргументы кладутся через `push` справа налево.
- После вызова caller чистит стек: `add esp, argument_count * 4`.
- Ответ часто удобно держать в `eax` и сразу печатать.
- Не рассчитывай на сохранность `eax`, `ecx`, `edx` после `printf` / `scanf`.

## Минимум после главы

Ты должен уметь:

- прочитать одно число;
- прочитать два-три числа;

- напечатать результат из `eax`;
- посчитать, сколько байт убрать из стека;
- найти ошибки `push [x]` для `scanf` и `push x` для `printf`.

Можно пока не заучивать:

- все детали CDECL;
- frame layout через `[ebp+8]`;
- stack alignment.

Подробный CDECL будет в [дне 17](/day_17) и на странице [C ABI / CDECL](/c_abi).


---

## Почему порядок `push` справа налево

C:

```c
printf("%d\n", x);
```

Аргументы:

```text
1: format string
2: x
```

CDECL кладёт их справа налево:

```asm
push dword [x]      ; second argument
push fmtOut         ; first argument
call printf
add esp, 8
```

Перед `call` стек выглядит так:

```text
higher addresses
+----------------+
| x              | second argument
+----------------+
| fmtOut         | first argument <- esp
+----------------+
lower addresses
```

---

## Почему после вызова `add esp, 8`

Один `push` в IA-32 кладёт 4 байта.

```text
2 arguments * 4 bytes = 8 bytes
```

Поэтому:

```asm
add esp, 8
```

Для трёх аргументов:

```asm
add esp, 12
```

Если ответ уже в `eax`, не надо сохранять его в память:

Но после `printf` нельзя считать, что `eax` всё ещё содержит ответ. `printf` имеет право испортить `eax`.

# День 07. Почему для `add` нет `iadd`

## Опора на материалы ВШЭ

`Slides2026-04.pdf`: арифметические команды, знаковая и беззнаковая интерпретация битовых векторов, флаги результата.

## Зачем этот день

В x86 есть пары:

```text
mul  / imul
div  / idiv
```

То есть unsigned-умножение и signed-умножение, unsigned-деление и signed-деление.

Но нет пары:

```text
add / iadd
sub / isub
```

На первый взгляд странно. В C++ же есть `int` и `unsigned int`. Почему процессору не нужны разные команды сложения?

Сегодня через этот вопрос мы разберём главное: **signed и unsigned — это часто не разные данные, а разные способы читать одни и те же биты**.

---

## Главная мысль

`add` складывает битовые векторы по модулю `2^w`, где `w` — размер операнда.

Для signed и unsigned сохраняемый битовый результат одинаковый.

Разница появляется в интерпретации:

- unsigned-смысл смотрит на `CF`;
- signed-смысл смотрит на `OF`.

---

## Самый короткий пример

Возьмём 8 бит.

```text
  11111111
+ 00000001
-----------
1 00000000
  ^^^^^^^^ stored result
```

В 8-битный результат сохраняется только:

```text
00000000
```

Теперь читаем это двумя способами.

### Как unsigned

```text
11111111 = 255
00000001 = 1
255 + 1 = 256
256 mod 256 = 0
```

Результат `0`, был перенос за пределы 8 бит. Это важно для `CF`.

### Как signed

```text
11111111 = -1
00000001 = 1
-1 + 1 = 0
```

Результат тоже `0`, и signed overflow здесь нет.

Биты результата одинаковые. Поэтому отдельная команда `iadd` не нужна.

---

## Что делает `add`

```asm
add eax, ebx
```

Это значит:

```cpp
eax = eax + ebx;
```

Важно: результат пишется в первый операнд.

До:

```text
eax = 10
ebx = 3
```

После:

```text
eax = 13
ebx = 3
```

`ebx` не меняется.

---

## Команды дня

| Команда | Пример | C++-смысл |
|---|---|---|
| `add` | `add eax, ebx` | `eax += ebx` |
| `sub` | `sub eax, 10` | `eax -= 10` |
| `inc` | `inc eax` | `eax++` |
| `dec` | `dec eax` | `eax--` |
| `neg` | `neg eax` | `eax = -eax` |

Пример:

```asm
mov eax, [a]
add eax, [b]
sub eax, 10
inc eax
dec eax
neg eax
```

Последняя команда:

```asm
neg eax
```

делает:

```text
eax = 0 - eax
```

---

## `inc` и `dec`

```asm
inc eax
```

почти как:

```asm
add eax, 1
```

```asm
dec eax
```

почти как:

```asm
sub eax, 1
```

Но есть тонкость: `inc/dec` не меняют `CF`, а `add/sub` меняют. Для первых задач это редко критично, но на уровне флагов это важно помнить.

Если не уверен, используй `add/sub`: они проще для рассуждений о флагах.

---

## `neg`: как получить минус

```asm
neg eax
```

Если:

```text
eax = 5
```

после `neg`:

```text
eax = -5
```

На уровне битов это two's complement:

```text
-x = ~x + 1
```

Например в 8 битах:

```text
5      = 00000101
~5     = 11111010
~5 + 1 = 11111011 = -5
```

---

## Флаги: пока только главное

После арифметики процессор обновляет флаги.

| Flag | Смысл |
|---|---|
| `CF` | carry/borrow для unsigned |
| `OF` | signed overflow |
| `ZF` | результат равен нулю |
| `SF` | старший бит результата |

### `CF`: unsigned-перенос

8-битно:

```text
255 + 1 -> 0, CF = 1
```

Почему? Потому что результат не поместился в 8 бит как unsigned.

### `OF`: signed overflow

8-битный signed диапазон:

```text
-128..127
```

```text
127 + 1 -> -128 по битам, OF = 1
```

Битовый результат есть, но как signed-математика он неправильный.

---

## Почему для деления есть `div/idiv`

Для сложения битовый результат совпадает.

Но для деления уже нет.

Один и тот же набор битов:

```text
0xFFFFFFFF
```

может означать:

```text
unsigned: 4294967295
signed:   -1
```

Теперь делим на 3:

```text
4294967295 / 3 = 1431655765
-1 / 3 = 0    ; в C-подобном целочисленном делении к нулю
```

Это совсем разные результаты. Поэтому у деления есть разные команды:

```asm
div   ; unsigned
idiv  ; signed
```

Умножение тоже имеет signed/unsigned формы, особенно когда нужен полный расширенный результат.

---


```asm

```

Это:

```cpp

```

## Мини-челленджи

### 1. `127 + 1` в 8 битах

Что получится по битам? Что с signed-смыслом?

<details>
<summary>Ответ</summary>

```text
01111111 + 00000001 = 10000000
```

По signed 8-bit это `-128`, хотя математически было `128`. Значит, signed overflow, `OF = 1`.

</details>

### 2. `255 + 1` в 8 битах

Что получится?

<details>
<summary>Ответ</summary>

```text
11111111 + 00000001 = 1 00000000
```

Сохраняется `00000000`, есть unsigned carry, `CF = 1`.

</details>

### 3. Почему нет `iadd`?

Скажи одной фразой.

<details>
<summary>Ответ</summary>

Потому что сохраняемый битовый результат сложения одинаков для signed и unsigned; отличается только интерпретация флагов.

</details>

### 4. Что меняет `add eax, ebx`?

<details>
<summary>Ответ</summary>

Меняет `eax` и флаги. `ebx` не меняется.

</details>

### 5. Что делает `neg eax`?

<details>
<summary>Ответ</summary>

Делает `eax = -eax`, то есть `0 - eax`.

</details>

| Ошибка | Почему плохо |
|---|---|

| путать `CF` и `OF` | `CF` для unsigned, `OF` для signed |
| читать `add eax, ebx` как чистое выражение | это `eax += ebx`, `eax` меняется |
| забывать, что `inc/dec` имеют особенность с `CF` | иногда лучше использовать `add/sub` |

# День 08. Как один байт становится `255` или `-1`

## Опора на материалы ВШЭ

`Slides2026-03.pdf`, `Slides2026-04.pdf`: `movsx`, `movzx`, `cbw`, `cwd`, `cdq`, знаковое расширение и подготовка к `idiv`.

## Зачем этот день

В C++ ты привык, что тип многое решает:

```cpp
signed char a = -1;
unsigned char b = 255;
```

Но на уровне битов это может быть одно и то же:

```text
11111111
```

Ассемблеру надо явно сказать, как маленькое значение превращать в большое: как signed или как unsigned.

Сегодня разбираем команды, которые делают это правильно:

```asm
movsx
movzx
cbw
cwd
cdq
```

---

## Главная мысль

`movzx` расширяет нулями.

`movsx` расширяет знаковым битом.

`cdq` расширяет знак `eax` в пару `edx:eax` перед signed-делением.

---

## Один байт, два смысла

Пусть в памяти лежит байт:

```text
0xFF = 11111111
```

Как unsigned 8-bit это:

```text
255
```

Как signed 8-bit это:

```text
-1
```

Биты одни и те же. Разная только интерпретация.

---

## Zero extension: `movzx`

```asm
movzx eax, byte [x]
```

Если:

```text
[x] = 0xFF
```

то после `movzx`:

```text
eax = 0x000000FF = 255
```

Картинка:

```text
source byte:
11111111

zero-extended dword:
00000000 00000000 00000000 11111111
```

То есть сверху просто добавили нули.

C++-аналогия:

```cpp
unsigned char x = 0xFF;
int y = x; // 255
```

---

## Sign extension: `movsx`

```asm
movsx eax, byte [x]
```

Если:

```text
[x] = 0xFF
```

то после `movsx`:

```text
eax = 0xFFFFFFFF = -1
```

Картинка:

```text
source byte:
11111111

sign-extended dword:
11111111 11111111 11111111 11111111
```

Почему добавились единицы?

Потому что старший бит исходного байта равен `1`. Для signed-числа это знак минуса. Расширение должно сохранить значение, поэтому знак “размножается”.

C++-аналогия:

```cpp
signed char x = -1;
int y = x; // -1
```

---

## Пример с `0x80`

Байт:

```text
0x80 = 10000000
```

Unsigned:

```text
128
```

Signed 8-bit:

```text
-128
```

`movzx`:

```text
00000000 00000000 00000000 10000000 = 128
```

`movsx`:

```text
11111111 11111111 11111111 10000000 = -128
```

Это один из лучших тестов на понимание темы.

---

## `movsx` и `movzx` с разными размерами

Примеры:

```asm
movsx eax, byte [x]   ; signed byte -> dword
movsx eax, word [x]   ; signed word -> dword

movzx eax, byte [x]   ; unsigned byte -> dword
movzx eax, word [x]   ; unsigned word -> dword
```

Важно: нельзя сделать `movzx` из 32 бит в 32 бита — расширять нечего.

---

## Зачем вообще это нужно

Представь C++:

```cpp
signed char c = -5;
int x = c + 10;
```

Перед сложением `c` надо расширить до `int` как signed.

Ассемблерная идея:

```asm
movsx eax, byte [c]
add eax, 10
```

А если:

```cpp
unsigned char c = 250;
int x = c + 10;
```

то нужно:

```asm
movzx eax, byte [c]
add eax, 10
```

Если перепутать `movsx` и `movzx`, результат может стать совсем другим.

---

## `cbw`, `cwd`, `cdq`

Это старые короткие команды знакового расширения.

| Команда | Что делает |
|---|---|
| `cbw` | `AL -> AX`, sign extension |
| `cwd` | `AX -> DX:AX`, sign extension |
| `cdq` | `EAX -> EDX:EAX`, sign extension |

Самая важная для нас:

```asm
cdq
```

Она смотрит на знак `eax`:

- если `eax >= 0`, делает `edx = 0`;
- если `eax < 0`, делает `edx = 0xFFFFFFFF`.

Зачем? Для signed division.

---

## Почему `cdq` нужен перед `idiv`

`idiv` делит не просто `eax`.

Он делит пару:

```text
edx:eax
```

То есть 64-битное signed-делимое, где `edx` — старшая часть, `eax` — младшая.

Если у нас есть 32-битное число в `eax`, перед `idiv` нужно правильно расширить его до `edx:eax`.

```asm
mov eax, [x]
cdq
idiv dword [y]
```

Если `x = 7`:

```text
eax = 00000007
edx = 00000000
```

Если `x = -7`:

```text
eax = FFFFFFF9
edx = FFFFFFFF
```

Так пара `edx:eax` действительно означает `-7` как 64-битное signed-число.

---

## Что будет, если забыть `cdq`

Плохо:

```asm
mov eax, [x]
idiv dword [y]
```

Почему плохо?

Потому что в `edx` может лежать старый мусор от предыдущих операций.

`idiv` будет делить не `x`, а непонятное число `edx:eax`.

Иногда программа просто упадёт с division error.

---

## Мини-пример: signed division

```asm
section .data
    fmtIn db "%d", 0
    fmtOut db "%d", 10, 0

section .bss
    x resd 1
    y resd 1

section .text
    extern scanf
    extern printf
    global main

main:
    push x
    push fmtIn
    call scanf
    add esp, 8

    push y
    push fmtIn
    call scanf
    add esp, 8

    mov eax, [x]
    cdq
    idiv dword [y]

    push eax        ; quotient
    push fmtOut
    call printf
    add esp, 8

    xor eax, eax
    ret
```

Чтобы напечатать остаток, надо печатать `edx`, а не `eax`.

# День 09. Деление: `edx:eax`, `div`, `idiv`

## Опора на материалы ВШЭ

`Slides2026-04.pdf`, `Slides2026-06.pdf`: `mul`, `imul`, `div`, `idiv`, пара `edx:eax`, подготовка делимого через `cdq`.

## За 30 секунд

- `div` — unsigned division.
- `idiv` — signed division.
- Делимое для 32-bit деления лежит в `edx:eax`.
- Делитель — один явный операнд.
- Частное после деления лежит в `eax`.
- Остаток после деления лежит в `edx`.
- Перед `idiv` обычно нужен `cdq`.
- Перед `div` обычно нужен `xor edx, edx`.

## Минимум после главы

Ты должен уметь:

- написать signed `a / b`;
- написать signed `a % b`;
- написать unsigned `a / b`;
- объяснить, зачем нужен `edx`;
- объяснить, почему забытый `cdq` ломает код;
- не писать несуществующее `idiv eax, ecx`.

Можно пока не заучивать:

- все формы `mul/imul`;
- overflow-детали полного 64-битного умножения;
- редкие исключения деления вне учебных задач.

---

## Главная схема

```text
Before division:

+----------------+----------------+
|      EDX       |      EAX       |
+----------------+----------------+
   high 32 bits      low 32 bits

idiv divisor

After division:

EAX = quotient
EDX = remainder
```

---

## Базовые шаблоны

### Signed division

```asm
mov eax, [x]
cdq
idiv dword [y]
; eax = x / y
; edx = x % y
```

### Unsigned division

```asm
mov eax, [x]
xor edx, edx
div dword [y]
; eax = x / y
; edx = x % y
```

---

## Почему не хватает одного `eax`

`idiv` не делит просто `eax`.

Для 32-bit деления процессор берёт 64-bit делимое из пары `edx:eax`.

Поэтому перед делением надо подготовить обе половины:

| Случай | Как подготовить |
|---|---|
| signed `int x` в `eax` | `cdq` |
| unsigned `uint32_t x` в `eax` | `xor edx, edx` |

---

## `cdq` перед `idiv`

`cdq` расширяет знак `eax` в `edx:eax`.

| `eax` | После `cdq`: `edx` | Смысл |
|---|---|---|
| положительный | `00000000h` | верхняя половина нулевая |
| отрицательный | `FFFFFFFFh` | знак размножен |

Пример для `x = -7`:

```text
eax = FFFFFFF9
edx = FFFFFFFF
edx:eax = FFFFFFFFFFFFFFF9 = -7 как 64-bit signed
```

---

## Умножение: что нужно знать сейчас

Для учебных задач чаще всего удобна форма:

```asm
imul eax, [b]        ; eax = eax * b
imul eax, ecx, 41    ; eax = ecx * 41
```

Есть и историческая форма:

```asm
mul ecx     ; unsigned: edx:eax = eax * ecx
imul ecx    ; signed:   edx:eax = eax * ecx
```

Но для первых задач обычно достаточно удобной формы `imul destination, source`.

---

## Полный пример: частное `a / b`

```asm
section .data
    fmtIn db "%d", 0
    fmtOut db "%d", 10, 0

section .bss
    a resd 1
    b resd 1

section .text
    extern scanf
    extern printf
    global main

main:
    push a
    push fmtIn
    call scanf
    add esp, 8

    push b
    push fmtIn
    call scanf
    add esp, 8

    mov eax, [a]
    cdq
    idiv dword [b]

    push eax
    push fmtOut
    call printf
    add esp, 8

    xor eax, eax
    ret
```

Чтобы напечатать остаток, печатай `edx`:

```asm
push edx
push fmtOut
call printf
add esp, 8
```

---

## Трассировка `-7 / 3`

```asm
mov eax, -7
cdq
mov ecx, 3
idiv ecx
```

| Шаг | EAX | EDX | ECX | Смысл |
|---|---|---|---|---|
| after `mov eax, -7` | `FFFFFFF9` | ? | ? | `eax = -7` |
| after `cdq` | `FFFFFFF9` | `FFFFFFFF` | ? | `edx:eax = -7` |
| after `mov ecx, 3` | `FFFFFFF9` | `FFFFFFFF` | `00000003` | делитель = 3 |
| after `idiv ecx` | `FFFFFFFE` | `FFFFFFFF` | `00000003` | quotient = -2, remainder = -1 |

---

## Что может пойти не так

| Ошибка | Почему плохо | Как правильно |
|---|---|---|
| забыть `cdq` перед `idiv` | `edx:eax` будет мусором | `mov eax,[x]` → `cdq` → `idiv ...` |
| забыть `xor edx, edx` перед `div` | unsigned-делимое будет неправильным | `mov eax,[x]` → `xor edx,edx` → `div ...` |
| писать `idiv eax, ecx` | такой формы нет | делитель один: `idiv ecx` |
| печатать `eax`, когда нужен остаток | остаток лежит в `edx` | `push edx` |
| использовать `div` для отрицательных чисел | `div` — unsigned | `idiv` + `cdq` |
| делить на ноль | runtime crash | проверить условие задачи |

## Главный branchless-паттерн

Если есть маска:

```text
mask = 00000000h  -> выбрать b
mask = FFFFFFFFh  -> выбрать a
```

то выбор без `if`:

```text
answer = (a & mask) | (b & ~mask)
```

NASM-shape:

```asm
; eax = a
; edx = b
; ecx = mask: 0 или -1

and eax, ecx
not ecx
and edx, ecx
or eax, edx
```

Главная ошибка: использовать маску `0/1`. Для выбора всего числа нужна маска `0/FFFFFFFFh`.

Подробнее: [Branchless-маски](/patterns/branchless).

Для `INT32_MIN` обычный положительный `abs` не помещается в signed 32-bit. В задачах нужно заранее определить, ожидается ли битовый результат `0x80000000`, более широкий тип или исключение этого входа ограничениями.

## `ceil(a / b)` для неотрицательных чисел

В задачах часто нужно округлить деление вверх.

```text
ceil(a / b) = (a + b - 1) / b
```

Для `a >= 0`, `b > 0`:

```asm
mov eax, [a]
add eax, [b]
dec eax
xor edx, edx
div dword [b]
; eax = ceil(a / b)
```

::: warning Граница формулы
Промежуточное `a + b - 1` может переполниться. Формула `(a + b - 1) / b` корректна только когда этот результат помещается в 32 бита. Если ограничения этого не гарантируют, считай `a / b` и отдельно прибавляй `1`, когда остаток ненулевой.
:::

Где пригодится:

- количество коробок в 01-14;
- количество задержанных коробок с номерами `0, 3, 6, ...`.

## 01-8. Masked merge

### Смысл

Для каждого бита выбрать:

## 01-16. Система уравнений

### Смысл

Дана система:

```text
(a11 & x) ^ (a12 & y) = b1
(a21 & x) ^ (a22 & y) = b2
```

Для одного бита есть четыре кандидата:

```text
x=0 y=0
x=1 y=0
x=0 y=1
x=1 y=1
```

Для каждого кандидата строим маску тех битов, где он подходит. Потом выбираем одно решение для каждого бита.

# День 11. EFLAGS: лампочки после инструкции

## Опора на материалы ВШЭ

`Slides2026-04.pdf`, `Slides2026-06.pdf`: регистр `EFLAGS`, арифметические флаги, влияние инструкций на флаги, подготовка к `cmp/test/jcc`.

## Зачем этот день

В C++ результат условия выглядит как `true` или `false`:

```cpp
if (x == y) { ... }
```

На уровне процессора обычно нет отдельного “булевого результата сравнения”. Вместо этого инструкция оставляет следы в специальном регистре флагов, а условный переход потом смотрит на эти следы.

То есть:

```text
операция -> флаги -> условный переход
```

Сегодня учимся понимать эти флаги. Без этого `cmp`, `test`, `je`, `jl`, `ja` будут выглядеть как магия.

---

## Главная мысль

Флаги — это признаки результата последней операции.

```text
+----+----+----+----+----+----+
| OF | SF | ZF | AF | PF | CF |
+----+----+----+----+----+----+
  |    |    |    |    |    +-- unsigned carry / borrow
  |    |    |    |    +------- parity of low byte
  |    |    |    +------------ auxiliary carry
  |    |    +----------------- zero result
  |    +---------------------- sign bit of result
  +--------------------------- signed overflow
```

Флаги живут до следующей инструкции, которая их изменит.

Это очень важно: условный переход смотрит не “на старую операцию вообще”, а на текущее состояние флагов.

---

## `ZF`: zero flag

`ZF = 1`, если результат операции равен нулю.

Пример:

```asm
mov eax, 5
sub eax, 5
```

После `sub`:

```text
eax = 0
ZF = 1
```

Ещё пример:

```asm
xor eax, eax
```

После него:

```text
eax = 0
ZF = 1
```

Поэтому `test eax, eax` + `je` часто используется для проверки на ноль. Подробно будет в следующем дне.

---

## `SF`: sign flag

`SF` равен старшему биту результата.

Для 32-битного результата:

```text
SF = bit 31
```

Если старший бит 1, signed-интерпретация обычно отрицательная.

Пример:

```text
result = 0xFFFFFFFF
SF = 1
```

Но осторожно: `SF=1` не всегда достаточно, чтобы сделать вывод “меньше” после сравнения. Для signed-сравнений ещё важен `OF`.

---

## `CF`: carry flag

`CF` показывает перенос или заём для unsigned-арифметики.

8-битный пример:

```text
  11111111   255
+ 00000001     1
-----------
1 00000000
```

В 8 битах сохранился ноль, а перенос ушёл наружу.

```text
CF = 1
```

Для unsigned это значит: результат не поместился.

Ещё пример с вычитанием:

```text
0 - 1
```

Для unsigned нужно занять за пределами диапазона, значит тоже будет borrow, то есть `CF=1`.

---

## `OF`: overflow flag

`OF` показывает signed overflow.

Signed 8-bit диапазон:

```text
-128..127
```

Пример:

```text
  01111111   127
+ 00000001     1
-----------
  10000000   -128 as signed
```

Математически должно быть `128`, но signed 8-bit не может это представить.

```text
OF = 1
```

Главное различие:

```text
CF -> unsigned overflow / carry
OF -> signed overflow
```

---

## `PF` и `AF`

Эти флаги реже нужны в обычных задачах, но в слайдах они есть, поэтому знать их стоит.

| Flag | Смысл |
|---|---|
| `PF` | parity flag: чётность количества единичных битов в младшем байте результата |
| `AF` | auxiliary carry: перенос между младшей и старшей половиной младшего байта; исторически важен для BCD |

Для экзамена чаще всего реально нужны:

```text
ZF, SF, CF, OF
```

Но если спрашивают “какие флаги есть в EFLAGS”, `PF` и `AF` тоже надо назвать.

---

## Какие инструкции меняют флаги

Упрощённая таблица:

| Инструкция | Что с флагами |
|---|---|
| `add`, `sub`, `cmp`, `neg` | обновляют арифметические флаги |
| `and`, `or`, `xor`, `test` | обновляют `ZF/SF/PF`, обычно сбрасывают `CF/OF` |
| `inc`, `dec` | обновляют почти как `add/sub`, но не меняют `CF` |
| `mov`, `lea` | не меняют флаги |
| `push`, `pop` | обычно не меняют флаги |
| `jmp`, `call`, `ret` | сами по себе не являются арифметикой; флаги не используют как результат вычисления |

Важное практическое правило:

> Если после `cmp` ты хочешь сделать `je`, не вставляй между ними инструкцию, которая меняет флаги.

---

## Главная ловушка: флаги легко перезаписать

Плохо:

```asm
cmp eax, ebx
add ecx, 1
je .equal
```

Почему плохо?

`je` должен был смотреть на результат `cmp eax, ebx`, но между ними стоит `add ecx, 1`. `add` изменил флаги. Теперь `je` смотрит уже на результат `add`, а не на сравнение.

Хорошо:

```asm
cmp eax, ebx
je .equal
add ecx, 1
```

Или так, если надо сохранить порядок действий:

```asm
add ecx, 1
cmp eax, ebx
je .equal
```

---

## `mov` не меняет флаги

Это полезно.

```asm
cmp eax, ebx
mov edx, 123
je .equal
```

`mov` не меняет флаги, поэтому `je` всё ещё смотрит на результат `cmp`.

Но такой стиль всё равно лучше использовать аккуратно: чем ближе `jcc` к `cmp/test`, тем проще читать код.

---

## Мини-примеры

### `xor eax, eax`

```asm
xor eax, eax
```

Результат:

```text
eax = 0
ZF = 1
CF = 0
OF = 0
```

Почему `CF/OF = 0`? Потому что логические операции вроде `xor` сбрасывают carry/overflow.

### `sub eax, eax`

```asm
sub eax, eax
```

Тоже даёт:

```text
eax = 0
ZF = 1
```

Но `xor eax, eax` обычно короче и идиоматичнее для обнуления.

### `test eax, eax`

```asm
test eax, eax
```

Значение `eax` не меняется, но флаги обновляются как после `eax & eax`.

Если `eax = 0`, будет `ZF=1`.

---

<details>

</details>

<details>
<summary>Ответ</summary>

</details>

### 3. Чем `CF` отличается от `OF`?

<details>
<summary>Ответ</summary>

`CF` нужен для unsigned-переноса/заёма. `OF` нужен для signed overflow.

</details>

### 4. Меняет ли `mov eax, ebx` флаги?

<details>
<summary>Ответ</summary>

Нет.

</details>

### 5. Что означает `ZF=1`?

<details>
<summary>Ответ</summary>

Результат последней флагоизменяющей операции был равен нулю.

</details>

---

## Типовые ошибки

| Ошибка | Почему плохо |
|---|---|
| думать, что флаги вечные | следующая инструкция может их изменить |
| вставлять `add/sub/and/xor` между `cmp` и `jcc` | переход будет смотреть не на те флаги |
| путать `CF` и `OF` | один unsigned, другой signed |
| думать, что `SF` один решает signed comparison | нужен ещё `OF` |
| считать, что `mov` обновляет флаги | `mov` флаги не меняет |

# День 12. `cmp`, `test` и условные переходы

## Опора на материалы ВШЭ

`Slides2026-06.pdf`: `CMP`, `TEST`, таблица `Jcc`, signed/unsigned comparisons и GOTO-форма условий.

## Зачем этот день

В C++ ты пишешь:

```cpp
if (x < y) { ... }
```

А в asm это раскладывается на две части:

```text
1. выставить флаги;
2. прыгнуть или не прыгнуть по этим флагам.
```

Сегодня разбираем команды, которые чаще всего стоят перед условными переходами:

```asm
cmp
test
```

И сами переходы:

```asm
je, jne, jl, jg, jb, ja, ...
```

---

## Главная мысль

`cmp a, b` — это как `a - b`, но результат не сохраняется.

`test a, b` — это как `a & b`, но результат не сохраняется.

Обе команды только выставляют флаги.

---

## 1. `cmp`: сравнение через вычитание

```asm
cmp eax, ebx
```

Мысленно:

```text
temp = eax - ebx
temp is not stored
flags are updated
```

Если `eax == ebx`, то:

```text
eax - ebx = 0
ZF = 1
```

Поэтому:

```asm
cmp eax, ebx
je .equal
```

значит:

```cpp
if (eax == ebx) goto equal;
```

---

### Важно: порядок операндов

```asm
cmp eax, ebx
```

это флаги как после:

```text
eax - ebx
```

Не `ebx - eax`.

Поэтому:

```asm
cmp eax, ebx
jl .less
```

означает:

```cpp
if ((int)eax < (int)ebx) goto less;
```

---

## 2. `test`: проверка битов

```asm
test eax, eax
```

Мысленно:

```text
temp = eax & eax
temp is not stored
flags are updated
```

Так как:

```text
eax & eax = eax
```

то `test eax,eax` удобно проверяет, равен ли `eax` нулю.

```asm
test eax, eax
je .zero
```

C++-смысл:

```cpp
if (eax == 0) goto zero;
```

Если нужно проверить конкретный бит:

```asm
test eax, 1
jne .odd
```

Это проверка младшего бита:

```cpp
if (eax & 1) goto odd;
```

---

## 3. Основные переходы

| Переход | Смысл |
|---|---|
| `jmp` | безусловный переход |
| `je` / `jz` | equal / zero |
| `jne` / `jnz` | not equal / not zero |
| `jg` | signed `>` |
| `jge` | signed `>=` |
| `jl` | signed `<` |
| `jle` | signed `<=` |
| `ja` | unsigned `>` |
| `jae` | unsigned `>=` |
| `jb` | unsigned `<` |
| `jbe` | unsigned `<=` |

`jz` и `je` — одно и то же по флагам: оба смотрят на `ZF=1`.

`jnz` и `jne` — тоже одно и то же: смотрят на `ZF=0`.

Разные имена нужны для читаемости:

```asm
cmp eax, ebx
je .equal      ; читается как equal

test eax, eax
jz .zero       ; читается как zero
```

---

## 4. Signed vs unsigned: `jl` не равно `jb`

Один и тот же набор битов:

```text
0xFFFFFFFF
```

как unsigned:

```text
4294967295
```

как signed:

```text
-1
```

Пусть:

```text
eax = 0xFFFFFFFF
ebx = 1
```

Signed-сравнение:

```text
-1 < 1
```

Unsigned-сравнение:

```text
4294967295 > 1
```

Поэтому после:

```asm
cmp eax, ebx
```

для signed будет верна идея:

```asm
jl .less_signed
```

а для unsigned:

```asm
ja .greater_unsigned
```

---

### Как выбрать переход

Если в C++ тип `int`, `short`, `char` как signed — думай про:

```text
jl, jle, jg, jge
```

Если тип `unsigned`, `size_t`, адреса, длины массивов — часто нужны:

```text
jb, jbe, ja, jae
```

Для равенства signed/unsigned не важно:

```text
je, jne
```

Потому что равенство битов одинаковое.

### `if (x == y)`

```asm

cmp eax, [y]
je .equal
```

### `if (x != 0)`

```asm
mov eax, [x]
test eax, eax
jne .not_zero
```

### `if ((int)x < (int)y)`

```asm

```


```asm
jne .bit_is_set
```

## 6. Почему `cmp` результат не сохраняет

Сравнение нужно не для того, чтобы получить число `a-b`, а чтобы узнать отношение между числами.

Если бы `cmp` сохранял результат, он портил бы регистры.

```asm
cmp eax, ebx
```

удобен тем, что:

```text
eax и ebx остаются прежними;
флаги обновляются.
```

Это как “примерить вычитание”, но не записывать результат.

---

## 7. Связь с C++ условиями

C++:

```cpp
if (x < y) {
    ans = 1;
}
```

ASM-shape:

```asm
mov eax, [x]
cmp eax, [y]
jge .skip
mov dword [ans], 1
.skip:
```

Почему `jge .skip`, а не `jl .then`?

Оба подхода возможны. В asm часто удобнее прыгнуть через тело, если условие не выполнено.

```text
если x >= y -> пропускаем then
иначе выполняем then
```

## 8. Типичная ловушка с флагами

Плохо:

```asm
cmp eax, ebx
add ecx, 1
jl .less
```

`add` поменял флаги. `jl` уже не относится к `cmp`.

Хорошо:

```asm
cmp eax, ebx
jl .less
add ecx, 1
```

Или:

```asm
add ecx, 1
cmp eax, ebx
jl .less
```

## 10. Типовые ошибки

| Ошибка | Почему плохо |
|---|---|
| читать `cmp eax, ebx` как `ebx-eax` | порядок именно `eax - ebx` |
| путать `jl` и `jb` | signed `<` против unsigned `<` |
| использовать `jg/ja` без понимания типа | тип сравнения выбирает переход |
| вставить флагоизменяющую команду между `cmp` и `jcc` | переход смотрит уже на другие флаги |
| использовать `cmp eax, 0` там, где проще `test eax,eax` | не ошибка, но `test` идиоматичнее |
| забыть, что `je` и `jz` одно и то же | разные имена для одного флага |

- выбрать `jl/jg` для signed;

# День 13. `if`, циклы и GOTO-форма

## Опора на материалы ВШЭ

`Slides2026-06.pdf`: GOTO-форма, `if/else`, циклы, `do while`, пример popcount и связь условий с `cmp/test/jcc`.

## Зачем этот день

В C++ у тебя есть красивые конструкции:

```cpp
if
while
for
do while
break
continue
```

В asm их нет.

И это не значит, что asm “бедный”. Просто процессору достаточно более простых вещей:

```text
метка
условный переход
безусловный переход
```

Сегодня мы учимся видеть за C++-конструкциями обычную GOTO-форму.

---

## Главная мысль

Управляющие конструкции C/C++ раскладываются в:

```asm
cmp / test
jcc
jmp
labels
```

То есть:

```text
условие -> флаги -> переход -> метка
```

---

## 1. Метки и `jmp`

Метка — это имя адреса в коде.

```asm
.loop:
    ; some code
    jmp .loop
```

`jmp` — безусловный переход.

```asm
jmp .end
```

значит:

```text
следующая инструкция будет по адресу .end
```

В C++ это ближе всего к:

```cpp
goto end;
```

---

## 2. Простой `if`

C++:

```cpp
if (x == 0) {
    y = 1;
}
```

ASM-shape:

```asm
mov eax, [x]
test eax, eax
jne .skip

mov dword [y], 1

.skip:
```

Почему `jne .skip`?

Мы хотим выполнить тело только если `x == 0`.

Значит, если `x != 0`, надо перепрыгнуть через тело.

```text
if not condition -> jump over body
body
skip:
```

Это очень частая форма.

---

## 3. `if/else`

C++:

```cpp
if (x > y) {
    result = x - y;
} else {
    result = y - x;
}
```

ASM-shape:

```asm
mov eax, [x]
cmp eax, [y]
jle .else

.then:
    mov eax, [x]
    sub eax, [y]
    mov [result], eax
    jmp .end

.else:
    mov eax, [y]
    sub eax, [x]
    mov [result], eax

.end:
```

Главный трюк:

```asm
jmp .end
```

после then-ветки.

Если его забыть, выполнение “провалится” в else, и else тоже выполнится.

---

### Почему иногда прыгают по обратному условию

В C++:

```cpp
if (x > y) {
    then_body;
}
```

В asm часто пишут:

```asm
cmp x, y
jle .skip
; then_body
.skip:
```

То есть если условие не выполнено, прыгаем через тело.

Это нормально. Не пытайся искать дословное `jg`, если в коде может быть `jle`.

---

## 4. `while`

C++:

```cpp
while (x != 0) {
    x >>= 1;
}
```

ASM-shape:

```asm
.loop:
    test eax, eax
    je .end

    shr eax, 1
    jmp .loop

.end:
```

Структура:

```text
.loop:
    проверить условие
    если условие ложное -> .end
    тело
    jmp .loop
.end:
```

---

## 5. `do while`

C++:

```cpp
do {
    x >>= 1;
} while (x != 0);
```

ASM-shape:

```asm
.loop:
    shr eax, 1
    test eax, eax
    jne .loop
```

Отличие от `while`:

```text
while    -> сначала проверка, потом тело
do while -> сначала тело, потом проверка
```

Поэтому `do while` всегда выполняет тело хотя бы один раз.

---

## 6. `for`

C++:

```cpp
for (int i = 0; i < n; ++i) {
    sum += i;
}
```

GOTO-форма:

```cpp
i = 0;
goto check;

loop:
    sum += i;
    ++i;

check:
    if (i < n) goto loop;
```

ASM-shape:

```asm
xor ecx, ecx        ; i = 0
xor eax, eax        ; sum = 0

.check:
    cmp ecx, [n]
    jge .end

    add eax, ecx
    inc ecx
    jmp .check

.end:
```

Здесь:

```text
ecx = i
eax = sum
```

---

## 7. `break` и `continue`

C++:

```cpp
while (...) {
    if (bad) break;
    if (skip) continue;
    body;
}
```

ASM-идея:

```asm
.loop:
    ; check loop condition
    je .end

    ; if bad -> break
    cmp ...
    je .end

    ; if skip -> continue
    cmp ...
    je .loop

    ; body
    jmp .loop

.end:
```

`break` — это `jmp` на конец цикла.

`continue` — это `jmp` на проверку или следующую итерацию.

---

## 8. Popcount-пример

Задача: посчитать количество единичных битов в числе.

C++:

```cpp
int result = 0;
while (x != 0) {
    result += x & 1;
    x >>= 1;
}
```

ASM:

```asm
xor ecx, ecx        ; result = 0

.loop:
    test edx, edx   ; x == 0?
    je .end

    mov eax, edx
    and eax, 1
    add ecx, eax

    shr edx, 1
    jmp .loop

.end:
```

Роли регистров:

```text
edx = x
ecx = result
eax = temporary x & 1
```

Разбор одной итерации:

```asm
mov eax, edx  ; скопировали x
and eax, 1    ; оставили младший бит
add ecx, eax  ; прибавили его к result
shr edx, 1    ; x >>= 1
```

---

## 9. Как читать чужой asm с циклами

Смотри не на конкретные имена меток, а на форму.

### Признак `while`

```asm
.loop:
    check
    jump_to_end_if_false
    body
    jmp .loop
.end:
```

### Признак `do while`

```asm
.loop:
    body
    check
    jump_to_loop_if_true
```

### Признак `if/else`

```asm
    check
    jump_to_else_if_false
.then:
    then_body
    jmp end
.else:
    else_body
.end:
```

# День 14. `switch`, jump table и fall-through

## Опора на материалы ВШЭ

`Slides2026-10.pdf`, `Slides2026-0xB.pdf`: `switch`, цепочки сравнений, таблицы переходов, fall-through, Duff’s Device и обратные задачи по восстановлению C-кода из asm.

## Зачем этот день

`if` и `while` обычно легко узнать по `cmp`, `jcc`, `jmp`.

А вот `switch` иногда выглядит странно:

```asm
jmp [.table + 4*eax]
```

Это не обычный переход на одну метку. Это переход по адресу, который лежит в таблице.

На экзамене такой код часто дают как reverse-задачу: нужно понять, какие были `case`, где `default`, какие ветки объединены и где есть fall-through.

---

## Главная мысль

Jump table — это массив адресов.

Индекс выбирает, на какую метку прыгнуть.

```text
index = value - minCase
jump to table[index]
```

В IA-32 адрес занимает 4 байта, поэтому часто видно:

```asm
jmp [.table + 4*eax]
```

---

## 1. `switch` как цепочка сравнений

Для маленького `switch` компилятор может сделать просто много сравнений.

C++:

```cpp
switch (x) {
    case 1: a = 10; break;
    case 2: a = 20; break;
    default: a = 0; break;
}
```

ASM-shape:

```asm
cmp eax, 1
je .case1
cmp eax, 2
je .case2
jmp .default

.case1:
    mov dword [a], 10
    jmp .end

.case2:
    mov dword [a], 20
    jmp .end

.default:
    mov dword [a], 0

.end:
```

Это похоже на `if/else if/else`.

---

## 2. `switch` как jump table

Если `case` идут плотным диапазоном, компилятору выгодно сделать таблицу адресов.

C++:

```cpp
switch (x) {
    case 0: goto case0;
    case 1: goto case1;
    case 2: goto case2;
    case 3: goto case3;
    default: goto def;
}
```

ASM-shape:

```asm
cmp eax, 3
ja .default
jmp [.table + 4*eax]

.table:
    dd .case0
    dd .case1
    dd .case2
    dd .case3
```

Разбор:

```asm
cmp eax, 3
ja .default
```

Если `eax > 3` как unsigned, значит индекс вне диапазона `0..3`, идём в default.

```asm
jmp [.table + 4*eax]
```

Берём адрес из таблицы:

```text
.table + 4*eax
```

Почему `4`? Потому что адрес в IA-32 занимает 4 байта.

---

## 3. Как выглядит таблица

```asm
.table:
    dd .case0
    dd .case1
    dd .case2
    dd .case3
```

Это почти как массив:

```cpp
void* table[] = { case0, case1, case2, case3 };
```

Если:

```text
eax = 2
```

то:

```text
.table + 4*2 = address of table[2]
```

В `table[2]` лежит адрес `.case2`, значит процессор прыгнет в `.case2`.

---

## 4. Почему используется unsigned-проверка `ja`

Часто перед таблицей видим:

```asm
cmp eax, max
ja .default
```

`ja` — unsigned `>`.

Это удобно: если `eax` вдруг отрицательный как signed, то как unsigned он станет огромным числом и тоже уйдёт в default.

Например:

```text
eax = -1 = FFFFFFFFh
```

Как unsigned это `4294967295`, значит точно `above max`.

---

## 5. Диапазон не с нуля

C++:

```cpp
switch (x) {
    case -2: ...
    case -1: ...
    case 0: ...
    case 1: ...
    case 2: ...
    case 3: ...
    case 4: ...
}
```

Чтобы использовать таблицу, компилятор может сдвинуть значение:

```asm
add eax, 2       ; eax = x + 2
cmp eax, 6       ; индексы 0..6
ja .default
jmp [.table + 4*eax]
```

Почему `+2`?

Чтобы:

```text
x = -2 -> index = 0
x = -1 -> index = 1
x =  0 -> index = 2
...
x =  4 -> index = 6
```

---

## 6. Разбор экзаменационного примера

```asm
add eax, 2
cmp eax, 6
ja .L2
jmp [.L8 + 4*eax]

section .rodata
.L8 dd .L3, .L2, .L4, .L5, .L6, .L6, .L7
```

Читаем по шагам.

### Шаг 1. Сдвиг диапазона

```asm
add eax, 2
```

Значит, исходный `x` превратили в `x + 2`.

Если индекс должен быть `0..6`, то исходные `x` были:

```text
x = -2..4
```

### Шаг 2. Проверка диапазона

```asm
cmp eax, 6
ja .L2
```

Если индекс больше 6 — default или особая ветка `.L2`.

### Шаг 3. Таблица

```asm
.L8 dd .L3, .L2, .L4, .L5, .L6, .L6, .L7
```

Таблица по индексам:

| Индекс | Исходный x | Метка |
|---:|---:|---|
| 0 | -2 | `.L3` |
| 1 | -1 | `.L2` |
| 2 | 0 | `.L4` |
| 3 | 1 | `.L5` |
| 4 | 2 | `.L6` |
| 5 | 3 | `.L6` |
| 6 | 4 | `.L7` |

`.L6` встречается два раза, значит `case 2` и `case 3` ведут в один код.

`.L2` используется и при выходе за диапазон, и для индекса 1. Это может означать, что `case -1` ведёт туда же, куда `default`.

---

## 7. Fall-through

В C/C++ у `switch` есть особенность: если не написать `break`, выполнение может провалиться в следующий `case`.

```cpp
switch (x) {
    case 1:
        a += 10;
        // no break
    case 2:
        a += 20;
        break;
}
```

В asm это может выглядеть как отсутствие `jmp .end` в конце одной ветки:

```asm
.case1:
    add dword [a], 10
    ; no jump here

.case2:
    add dword [a], 20
    jmp .end
```

Если видишь, что ветка не заканчивается переходом к `.end`, а код просто продолжается следующей меткой — это может быть fall-through.

---

## 8. Duff’s Device — зачем его вообще показывают

Duff’s Device — это странный C-трюк, где `switch` смешивается с циклом и fall-through.

Тебе не нужно писать такое в задачах. Важно понять идею:

- `case` в C — это метки внутри блока;
- выполнение может “проваливаться” дальше;
- поэтому `switch` не всегда похож на аккуратный набор независимых веток.

Для курса это нужно не как стиль программирования, а как способ понять, насколько напрямую C-конструкции могут отображаться в переходы.

---

## 9. Паттерны для reverse engineering

| Pattern | Meaning |
|---|---|
| `cmp eax, max` + `ja default` | проверка выхода за диапазон |
| `sub eax, min` или `add eax, const` | сдвиг диапазона case к нулю |
| `jmp [table + 4*eax]` | переход по jump table |
| одинаковая метка в таблице | несколько `case` ведут в одну ветку |
| default-метка в таблице | некоторый `case` объединён с default |
| нет `jmp .end` в конце case | возможно fall-through |
| таблица в `.rodata` | массив адресов/констант |

<details>

# День 15. Адресация и `lea`: массивы без магии

## Опора на материалы ВШЭ

`Slides2026-05.pdf`, `Slides2026-10.pdf`: виды адресации, `LEA`, массивы, row-major layout, оптимизация доступа к массивам и обратные задачи по адресным формулам.

## Зачем этот день

В C++ ты пишешь просто:

```cpp
a[i]
a[i][j]
s.field
```

Но процессор не знает ни `i`, ни `field`, ни “двумерный массив”. Он знает адреса.

Сегодня мы разбираем главную формулу памяти в x86:

```asm
[base + index * scale + displacement]
```

Если она станет понятной, массивы, структуры и reverse engineering станут намного проще.

---

## Главная мысль

Квадратные скобки означают обращение к памяти.

`lea` считает адрес, но память не читает.

```asm
mov eax, [edx + 4*ecx]   ; прочитать значение по адресу
lea eax, [edx + 4*ecx]   ; посчитать сам адрес
```

---

## 1. Общая форма адреса

В x86 можно адресовать память так:

```text
[ base + index * scale + displacement ]
```

Пример:

```asm
[eax + ecx*4 + 8]
```

Разбор:

| Часть | Значение |
|---|---|
| base | `eax` |
| index | `ecx` |
| scale | `4` |
| displacement | `8` |

То есть адрес равен:

```text
eax + ecx * 4 + 8
```

`scale` может быть только:

```text
1, 2, 4, 8
```

Почему именно такие? Потому что это удобно для размеров элементов массивов: `char`, `short`, `int`, `long long`.

---

## 2. Простые формы адресации

| Форма | Пример | Где встречается |
|---|---|---|
| `[base]` | `[eax]` | указатель |
| `[base + disp]` | `[ebp-4]` | локальная переменная/поле |
| `[base + index]` | `[eax+ecx]` | byte-массив |
| `[base + index*scale]` | `[eax+4*ecx]` | `int a[i]` |
| `[base + index*scale + disp]` | `[eax+4*ecx+8]` | массив внутри структуры |

Пример:

```asm
mov eax, [ebp-4]
```

может означать “прочитать локальную переменную”.

```asm
mov eax, [edx+4*ecx]
```

может означать “прочитать `int`-элемент массива”.

---

## 3. `mov` против `lea`

Это одна из главных ловушек.

```asm
mov eax, [edx + 4*ecx]
```

значит:

```cpp
eax = *(int*)(edx + 4*ecx);
```

То есть память читается.

А:

```asm
lea eax, [edx + 4*ecx]
```

значит:

```cpp
eax = edx + 4*ecx;
```

Память не читается.

Таблица:

| Инструкция | Читает память? | Смысл |
|---|---:|---|
| `mov eax, [addr]` | да | загрузить значение из памяти |
| `lea eax, [addr]` | нет | посчитать адрес/арифметику |

---

### Почему `lea` называется странно

`lea` = load effective address.

Название может сбить с толку: “load” звучит так, будто мы что-то читаем из памяти.

Но на практике:

```asm
lea eax, [ebx + 4*ecx + 8]
```

просто считает:

```text
eax = ebx + 4*ecx + 8
```

Это можно использовать не только для адресов, но и как удобную арифметику:

```asm
lea eax, [eax + 2*eax] ; eax = eax * 3
```

---

## 4. Одномерный массив

C++:

```cpp
int a[5];
```

В памяти:

```text
a+0    a+4    a+8    a+12   a+16
+------+------+------+------+------+
| a[0] | a[1] | a[2] | a[3] | a[4] |
+------+------+------+------+------+
```

Почему шаг 4?

Потому что `int` занимает 4 байта.

Адрес:

```text
&a[i] = base + 4*i
```

Если:

```text
edx = base address of a
ecx = i
```

то:

```asm
mov eax, [edx + 4*ecx] ; eax = a[i]
lea eax, [edx + 4*ecx] ; eax = &a[i]
```

---

## 5. Массивы разных типов

| C/C++ type | Size | Address of `arr[i]` |
|---|---:|---|
| `char` | 1 | `base + i` |
| `short` | 2 | `base + 2*i` |
| `int` | 4 | `base + 4*i` |
| `long long` | 8 | `base + 8*i` |

Примеры:

```asm
; char c[i]
movzx eax, byte [edx + ecx]

; short s[i]
movsx eax, word [edx + 2*ecx]

; int a[i]
mov eax, [edx + 4*ecx]

; long long q[i], младшая/старшая часть отдельно в IA-32
mov eax, [edx + 8*ecx]
mov edx, [edx + 8*ecx + 4]
```

Для `char`/`short` часто нужны `movsx` или `movzx`, потому что читаем меньше 32 бит.

---

## 6. Двумерный массив: row-major

C/C++ хранит двумерные массивы по строкам.

```cpp
int a[R][C];
```

Логически:

```text
row 0: a[0][0] a[0][1] a[0][2]
row 1: a[1][0] a[1][1] a[1][2]
```

В памяти:

```text
a[0][0] a[0][1] a[0][2] a[1][0] a[1][1] a[1][2]
```

Адрес:

```text
&a[i][j] = base + sizeof(int) * (i*C + j)
```

Для `int`:

```text
&a[i][j] = base + 4 * (i*C + j)
```

Если `C = 10`:

```text
&a[i][j] = base + 4 * (10*i + j)
```

---

### Пример 2D

C++:

```cpp
int a[3][5];
int x = a[i][j];
```

Формула:

```text
address = base + 4 * (i*5 + j)
```

ASM-идея:

```asm
mov eax, [i]
imul eax, 5
add eax, [j]
mov eax, [base + 4*eax]
```

Если base в `edx`:

```asm
mov eax, [i]
imul eax, 5
add eax, [j]
mov eax, [edx + 4*eax]
```

---

## 7. Почему проход по строкам быстрее прохода по столбцам

Для C/C++ row-major массива:

```cpp
int a[R][C];
```

элементы одной строки лежат рядом.

Хорошо:

```cpp
for (int i = 0; i < R; ++i)
    for (int j = 0; j < C; ++j)
        sum += a[i][j];
```

Плохо для cache locality:

```cpp
for (int j = 0; j < C; ++j)
    for (int i = 0; i < R; ++i)
        sum += a[i][j];
```

Почему?

Первый вариант идёт по памяти почти подряд.

Второй прыгает через целые строки.

На уровне адресов это видно напрямую:

```text
a[i][j+1] рядом с a[i][j]
a[i+1][j] далеко на C элементов
```

---

## 8. Адресация внутри структуры

Пока структуры подробно будут в дне 19, но адресная формула уже готовит к ним.

```asm
[eax + 4*ecx + 8]
```

может означать:

```cpp
obj->a[i]
```

если:

```text
eax = address of obj
8   = offset of field a
4   = sizeof(int)
ecx = i
```

То есть `+8` часто значит “смещение поля внутри структуры”.

---

## 9. Reverse-задачи по формулам адреса

Если видишь:

```asm
mov eax, [edx + 4*ecx]
```

возможный смысл:

```cpp
eax = a[i]; // int array
```

Если видишь:

```asm
movzx eax, byte [edx + ecx]
```

возможный смысл:

```cpp
eax = (unsigned char)c[i];
```

Если видишь:

```asm
movsx eax, word [edx + 2*ecx]
```

возможный смысл:

```cpp
eax = (int)(short)s[i];
```

Если видишь:

```asm
lea eax, [edx + 4*ecx]
```

возможный смысл:

```cpp
eax = &a[i];
```

---

## 10. Мини-челленджи

#### 1. `mov` или `lea`

Чем отличаются?

```asm
mov eax, [edx + 4*ecx]
lea eax, [edx + 4*ecx]
```

<details>
<summary>Ответ</summary>

`mov` читает значение из памяти по адресу `edx + 4*ecx`.

`lea` просто считает адрес `edx + 4*ecx`.

</details>

#### 2. Адрес `short s[i]`

Если `edx = base`, `ecx = i`, какой адрес?

<details>
<summary>Ответ</summary>

```asm
[edx + 2*ecx]
```

</details>

#### 3. Адрес `int a[i][j]`

В строке `C` столбцов. Формула?

<details>
<summary>Ответ</summary>

```text
base + 4 * (i*C + j)
```

</details>

#### 4. Что может означать `+8`?

```asm
[eax + 4*ecx + 8]
```

<details>
<summary>Ответ</summary>

Например, смещение поля-массива внутри структуры: `obj->a[i]`, где `a` начинается с offset 8.

</details>

#### 5. Как прочитать `unsigned char c[i]`?

<details>
<summary>Ответ</summary>

```asm
movzx eax, byte [base + i]
```

Например:

```asm
movzx eax, byte [edx + ecx]
```

</details>

---

## 11. Типовые ошибки

| Ошибка | Почему плохо |
|---|---|
| думать, что `lea` читает память | `lea` только считает адрес |
| забыть умножение на размер элемента | `int a[i]` — это `base + 4*i` |
| перепутать row-major и column-major | формула `i*C+j`, не `j*R+i` |
| использовать `mov eax, [charArray+i]` без `byte/movzx` | прочитаешь лишние байты |
| не учитывать `+offset` поля структуры | попадёшь не в тот field |
| забыть, что scale только 1/2/4/8 | нельзя напрямую `[eax+3*ecx]` |

---

## 12. Что должно остаться в голове

После этого дня ты должен уметь:

- читать форму `[base + index*scale + displacement]`;
- объяснять разницу `mov` и `lea`;
- считать адрес `char/short/int/long long arr[i]`;
- считать адрес `int a[i][j]` в row-major;
- понимать, почему проход по строкам обычно лучше;
- видеть в `[eax+4*ecx+8]` возможный доступ к массиву внутри структуры.

Если ты можешь по asm-адресу восстановить C-подобный смысл, день закрыт.

## Практический мост: большие массивы

Многие задачи дают `N` до сотен тысяч. В `.bss` можно заранее зарезервировать массив:

```asm
section .bss
    arr resd 500000
```

Обращение к `arr[i]`:

```asm
mov eax, [arr + 4*ecx]
mov [arr + 4*ecx], eax
```

Если в задаче надо много раз переставлять сегменты, физически двигать массив может быть слишком медленно. Тогда смотри [Массивная связность](/patterns/array_linked_list).

# День 16. Стек: стопка, которая растёт вниз

## Опора на материалы ВШЭ

`Slides2026-07.pdf`: стек IA-32, `esp`, `push`, `pop`, `call`, `ret`, адрес возврата и базовая механика вызова функций.

## Зачем этот день

До этого мы работали в основном с регистрами, памятью, флагами и переходами.

Теперь появляется стек. Без него невозможно нормально понять:

- вызовы функций;
- рекурсию;
- аргументы функций;
- локальные переменные;
- адрес возврата;
- почему `scanf/printf` требуют `add esp, ...`;
- почему выход за границы массива на стеке может быть опасен.

Стек — одна из главных тем всего курса.

---

## Главная мысль

Стек IA-32 растёт к меньшим адресам.

`esp` указывает на верхушку стека.

```text
higher addresses
+------------------+
| older stack data |
+------------------+
|                  |
+------------------+ <- esp
lower addresses
```

Когда мы кладём значение на стек, `esp` уменьшается.

Когда снимаем значение со стека, `esp` увеличивается.

---

## 1. Что такое стек

Стек — это структура LIFO:

```text
last in, first out
```

То есть последним положили — первым достали.

Пример:

```asm
push 10
push 20
pop eax
pop ebx
```

Результат:

```text
eax = 20
ebx = 10
```

Потому что `20` лежало на верхушке.

---

## 2. Почему стек растёт вниз

В IA-32 стек растёт в сторону меньших адресов.

Это может быть непривычно: “кладём значение”, а адрес уменьшается.

Но для x86 это норма.

```text
Before push eax:

0x100C | old data |
0x1008 | old data | <- esp

After push eax:

0x100C | old data |
0x1008 | old data |
0x1004 |   eax    | <- esp
```

То есть:

```text
push -> esp -= 4
```

---

## 3. `push`

```asm
push eax
```

примерно значит:

```text
esp = esp - 4
[esp] = eax
```

Почему 4?

Потому что в IA-32 обычный `push` кладёт 32-битное значение, то есть `dword`.

Пример:

```text
eax = 123
esp = 0x1008
```

После:

```asm
push eax
```

получим:

```text
esp = 0x1004
[0x1004] = 123
```

---

## 4. `pop`

```asm
pop eax
```

примерно значит:

```text
eax = [esp]
esp = esp + 4
```

Пример:

```text
esp = 0x1004
[0x1004] = 123
```

После:

```asm
pop eax
```

получим:

```text
eax = 123
esp = 0x1008
```

Важно: `pop` не обязательно “стирает” память. Он просто двигает `esp`. Старые байты могут физически оставаться в памяти, но они больше не считаются верхушкой стека.

---

## 5. Баланс стека

Если ты сделал:

```asm
push eax
push ebx
```

то стек уменьшился на 8 байт.

Чтобы вернуться к прежнему `esp`, нужно либо:

```asm
pop ebx
pop eax
```

либо, если значения не нужны:

```asm
add esp, 8
```

Именно поэтому после:

```asm
push x
push fmt
call scanf
```

мы делаем:

```asm
add esp, 8
```

Аргументы больше не нужны, их можно убрать со стека.

---

## 6. `call`: прыжок с запиской

`call f` — это не просто `jmp f`.

`jmp` просто прыгает.

`call` прыгает и сохраняет адрес возврата.

```text
call f:
1. push address_after_call
2. jump to f
```

То есть:

```asm
call f
```

мысленно похоже на:

```asm
push return_address
jmp f
```

Только процессор делает это сам.

---

## 7. `ret`: вернуться по записке

```asm
ret
```

примерно значит:

```text
1. pop return_address
2. jump to return_address
```

То есть `ret` берёт адрес с вершины стека и передаёт управление туда.

Поэтому если стек испорчен, `ret` может прыгнуть куда угодно.

Это одна из причин, почему стек настолько важен для безопасности.

---

## 8. Как выглядит стек при `call`

Перед:

```asm
call f
```

```text
esp -> [ old stack data ]
```

Сразу внутри `f`:

```text
esp -> [ return address ]
       [ old stack data  ]
```

Потом функция может сама класть на стек локальные данные, сохранять регистры и т.д.

---

## 9. Функция без аргументов

Простейшая функция:

```asm
f:
    mov eax, 123
    ret
```

Вызов:

```asm
call f
; после возврата eax = 123
```

Здесь `eax` используется как возвращаемое значение — это обычная CDECL-идея, которую подробно разберём в следующем дне.

---

## 10. Почему рекурсия требует стек

C++:

```cpp
int fact(int n) {
    if (n <= 1) return 1;
    return n * fact(n - 1);
}
```

Каждый вызов `fact` должен помнить:

- своё значение `n`;
- куда вернуться;
- временные значения;
- иногда сохранённые регистры.

Если вызовы вложенные, всё это складывается на стек:

```text
fact(5)
  fact(4)
    fact(3)
      fact(2)
        fact(1)
```

Каждый уровень имеет свой кусок стека.

---

## 11. Мини-трассировка

Код:

```asm
push 1
push 2
push 3
pop eax
pop ebx
```

После трёх `push`:

```text
esp -> [ 3 ]
       [ 2 ]
       [ 1 ]
```

После `pop eax`:

```text
eax = 3
esp -> [ 2 ]
       [ 1 ]
```

После `pop ebx`:

```text
ebx = 2
esp -> [ 1 ]
```

`1` всё ещё лежит на стеке.

---

## 12. Что нельзя делать со стеком

### Плохо: лишний `pop`

```asm
push eax
pop ebx
pop ecx ; лишний pop
```

Второй `pop` снимет что-то, что ты не клал специально. Это может быть старое значение, адрес возврата или часть чужого фрейма.

### Плохо: забыть очистить аргументы

```asm
push x
push fmt
call printf
; забыли add esp, 8
```

`esp` остаётся ниже, чем должен. Следующие вызовы/возвраты могут работать неправильно.

### Плохо: менять `esp` без понимания

```asm
sub esp, 100
; ...
ret
```

Если не вернуть `esp` обратно, `ret` возьмёт адрес возврата не оттуда.

---

## 13. Мини-челленджи

#### 1. Нарисуй стек

После:

```asm
push 1
push 2
push 3
```

что лежит на верхушке?

<details>
<summary>Ответ</summary>

На верхушке лежит `3`, ниже `2`, ниже `1`.

</details>

#### 2. Что будет в регистрах?

```asm
push 10
push 20
pop eax
pop ebx
```

<details>
<summary>Ответ</summary>

```text
eax = 20
ebx = 10
```

</details>

#### 3. Объясни `call` двумя действиями

<details>
<summary>Ответ</summary>

`call` кладёт адрес возврата на стек и переходит к функции.

</details>

#### 4. Объясни `ret` двумя действиями

<details>
<summary>Ответ</summary>

`ret` снимает адрес возврата со стека и прыгает по нему.

</details>

#### 5. Почему `add esp, 8` после двух аргументов?

<details>
<summary>Ответ</summary>

Каждый аргумент занимает 4 байта. Два аргумента — 8 байт.

</details>

---

## 14. Типовые ошибки

| Ошибка | Почему плохо |
|---|---|
| думать, что стек растёт вверх | в IA-32 `push` уменьшает `esp` |
| забывать, что `push/pop` меняют `esp` | ломается баланс стека |
| делать лишний `pop` | можно снять адрес возврата или чужие данные |
| забывать `add esp, ...` после CDECL-вызова | стек остаётся загрязнённым аргументами |
| менять `esp` и не восстанавливать | `ret` возьмёт адрес не оттуда |
| думать, что `call` — это просто `jmp` | `call` ещё сохраняет адрес возврата |

---

После этого дня ты должен уметь:

- нарисовать стек до и после `push`;
- объяснить, почему стек растёт вниз;
- объяснить `push` как `esp -= 4; [esp] = value`;
- объяснить `pop` как `value = [esp]; esp += 4`;
- объяснить `call` и `ret` через адрес возврата;
- понимать, почему стек нужно держать сбалансированным;
- понимать, почему рекурсия использует стек.

Если ты можешь вручную протрассировать 5–6 `push/pop/call/ret`, день усвоен.

# День 17. Фрейм функции и CDECL

## Опора на материалы ВШЭ

`Slides2026-07.pdf`, `Slides2026-08.pdf`: фреймы функций, `ebp`, CDECL, порядок аргументов, сохранение регистров, возвращаемое значение и рекурсия.

## Зачем этот день

В прошлом дне мы разобрали стек, `push`, `pop`, `call`, `ret`.

Теперь главный вопрос:

> Функция вызвалась. Как она понимает, где её аргументы, где локальные переменные и куда возвращать результат?

Ответ: через **стековый фрейм** и соглашение вызова **CDECL**.

Это одна из самых экзаменационных тем. Если ты понимаешь `[ebp+8]`, `[ebp-4]` и `add esp, 8`, половина ассемблерных листингов становится намного понятнее.

---

## Главная мысль

В классическом IA-32 CDECL:

```text
аргументы лежат выше ebp;
адрес возврата лежит по [ebp+4];
старый ebp лежит по [ebp];
локальные переменные лежат ниже ebp;
возвращаемое значение обычно в eax.
```

Карта:

```text
higher addresses
+------------------+
| argument 3       | [ebp+16]
+------------------+
| argument 2       | [ebp+12]
+------------------+
| argument 1       | [ebp+8]
+------------------+
| return address   | [ebp+4]
+------------------+
| old ebp          | [ebp]
+------------------+
| local variable 1 | [ebp-4]
+------------------+
| local variable 2 | [ebp-8]
+------------------+
lower addresses
```

---

## 1. Что такое фрейм функции

Фрейм функции — это кусок стека, который принадлежит конкретному вызову функции.

В нём могут быть:

- адрес возврата;
- старое значение `ebp`;
- аргументы;
- локальные переменные;
- временные значения;
- сохранённые регистры.

Если функция вызывается рекурсивно, каждый вызов получает свой фрейм.

```text
fact(5) frame
fact(4) frame
fact(3) frame
fact(2) frame
fact(1) frame
```

Именно поэтому локальные переменные рекурсивных вызовов не смешиваются.

---

## 2. Пролог функции

Классический пролог:

```asm
push ebp
mov ebp, esp
sub esp, N
```

Разберём.

### `push ebp`

Сохраняем старый `ebp`, чтобы потом вернуть фрейм вызывающей функции.

```text
esp -> [ old ebp ]
```

### `mov ebp, esp`

Теперь `ebp` становится стабильной базой текущего фрейма.

Почему нужен `ebp`, если есть `esp`?

Потому что `esp` меняется при `push`, `pop`, выделении временных данных. А `ebp` остаётся удобной точкой отсчёта.

### `sub esp, N`

Выделяем место под локальные переменные.

```asm
sub esp, 16
```

значит: зарезервировать 16 байт ниже `ebp`.

---

## 3. Эпилог функции

Классический эпилог:

```asm
mov esp, ebp
pop ebp
ret
```

Разберём.

### `mov esp, ebp`

Выкидываем локальные переменные: возвращаем `esp` к началу фрейма.

### `pop ebp`

Восстанавливаем старый `ebp` вызывающей функции.

### `ret`

Снимаем адрес возврата со стека и прыгаем обратно.

---

## 4. `leave`

Команда:

```asm
leave
```

примерно эквивалентна:

```asm
mov esp, ebp
pop ebp
```

Поэтому часто можно увидеть:

```asm
leave
ret
```

Это просто короткая форма эпилога.

---

## 5. Почему первый аргумент — `[ebp+8]`

После входа в функцию и пролога стек устроен так:

```text
[ebp+12]  second argument
[ebp+8]   first argument
[ebp+4]   return address
[ebp]     old ebp
[ebp-4]   local variable
```

Почему не `[ebp+4]`?

Потому что `[ebp+4]` уже занят адресом возврата, который положил `call`.

Почему не `[ebp]`?

Потому что `[ebp]` — сохранённый старый `ebp`.

Поэтому:

```text
first argument = [ebp+8]
```

Это нужно довести до автоматизма.

---

## 6. CDECL: правила вызова

CDECL — соглашение о том, как C-функции вызывают друг друга в 32-битном x86.

Главные правила:

| Правило | Что значит |
|---|---|
| arguments right-to-left | аргументы кладутся на стек справа налево |
| caller cleans stack | вызывающий после `call` делает `add esp, ...` |
| return value in `eax` | обычный `int` возвращается в `eax` |
| `edx:eax` for some 64-bit results | 64-битный integer может возвращаться через пару регистров |
| `eax/ecx/edx` caller-saved | функция может их испортить |
| `ebx/esi/edi` callee-saved | функция должна восстановить, если использовала |

---

## 7. Пример функции `sum`

C:

```c
int sum(int a, int b) {
    return a + b;
}
```

NASM:

```asm
sum:
    push ebp
    mov ebp, esp

    mov eax, [ebp+8]     ; a
    add eax, [ebp+12]    ; a + b

    pop ebp
    ret
```

Здесь:

```text
[ebp+8]  = a
[ebp+12] = b
eax      = return value
```

---

## 8. Вызов `sum`

C:

```c
int z = sum(a, b);
```

NASM:

```asm
push dword [b]
push dword [a]
call sum
add esp, 8
; eax = result
```

Почему сначала `b`, потом `a`?

Потому что CDECL кладёт аргументы справа налево.

Почему `add esp, 8`?

Два аргумента по 4 байта.

---

## 9. Локальные переменные

C:

```c
int f(int x) {
    int y;
    y = x + 1;
    return y * 2;
}
```

NASM-идея:

```asm
f:
    push ebp
    mov ebp, esp
    sub esp, 4          ; local y

    mov eax, [ebp+8]    ; x
    add eax, 1
    mov [ebp-4], eax    ; y = x + 1

    mov eax, [ebp-4]
    imul eax, 2

    mov esp, ebp
    pop ebp
    ret
```

Здесь:

```text
[ebp+8] = x
[ebp-4] = y
```

---

## 10. Caller-saved и callee-saved

Когда функция вызывается, нужно договориться, какие регистры кто сохраняет.

### Caller-saved

```text
eax, ecx, edx
```

Вызывающий не должен надеяться, что эти регистры сохранятся после вызова.

Если caller хочет сохранить их значения, он сам должен это сделать:

```asm
push eax
call f
pop eax
```

или сохранить в память.

### Callee-saved

```text
ebx, esi, edi
```

Если функция хочет использовать их, она должна восстановить перед возвратом.

```asm
my_func:
    push ebp
    mov ebp, esp
    push ebx

    ; use ebx

    pop ebx
    pop ebp
    ret
```

---

## 11. Почему `printf` портит регистры

Когда ты вызываешь:

```asm
call printf
```

после возврата нельзя рассчитывать, что `eax`, `ecx`, `edx` остались прежними.

Если перед `printf` в `eax` был важный ответ, а после `printf` ты снова хочешь его использовать, надо сохранить.

Например:

```asm
push eax
push eax
push fmtOut
call printf
add esp, 8
pop eax
```

Но часто проще: посчитать, напечатать и больше не использовать.

## 12. Рекурсия и фреймы

C:

```c
int fact(int n) {
    if (n <= 1) return 1;
    return n * fact(n - 1);
}
```

Каждый вызов имеет свой `[ebp+8]`, свой return address, свои локальные значения.

```text
fact(5): [ebp+8] = 5
fact(4): [ebp+8] = 4
fact(3): [ebp+8] = 3
...
```

Это возможно потому, что каждый `call` создаёт новый фрейм на стеке.

#### 1. Где второй аргумент?

<details>
<summary>Ответ</summary>

`[ebp+12]`.

</details>

#### 2. Почему локальные переменные имеют отрицательные смещения?

<details>
<summary>Ответ</summary>

Потому что стек растёт вниз, и локальные переменные выделяются ниже `ebp`.

</details>

#### 3. Напиши `square(x)`

C:

<details>
<summary>Ответ</summary>


</details>

#### 4. Почему после `call sum` нужно `add esp, 8`?

<details>

#### 5. Какие регистры callee должен восстановить?

<details>

## 14. Типовые ошибки

| Ошибка | Почему плохо |
|---|---|
| считать первый аргумент `[ebp+4]` | там return address |
| забыть восстановить `ebp` | ломается фрейм вызывающей функции |
| использовать `ebx` и не восстановить | нарушается CDECL |
| забыть `add esp, ...` после вызова | caller не очистил аргументы |
| хранить важное значение в `eax` перед `call` | функция может испортить `eax` |
| перепутать локальные и аргументы | локальные ниже `ebp`, аргументы выше |

# День 18. Reverse engineering: читаем asm как следы C

## Опора на материалы ВШЭ

`Slides2026-08.pdf`: обратная задача по CDECL, восстановление типов, аргументов, порядка параметров и объявления функции по ассемблерному фрагменту.

## Зачем этот день

Это день-детектив.

До этого мы учились писать asm. Но на экзамене часто бывает обратная ситуация: тебе дают фрагмент ассемблера и спрашивают, что он делает.

Важно не пытаться восстановить исходный C-код идеально. Это почти невозможно: разные C-программы могут дать очень похожий asm.

Цель другая:

```text
понять смысл функции:
аргументы -> типы -> действия -> return value
```

---

## Главная мысль

Reverse engineering asm — это не гадание. Это набор признаков.

Ты смотришь на:

- откуда читаются аргументы;
- какими размерами читается память;
- есть ли `movsx` или `movzx`;
- используется ли значение как адрес;
- что попадает в `eax` перед `ret`;
- какие переходы образуют условия и циклы.

---

## 1. Базовая карта CDECL

Если функция использует классический фрейм:

```asm
push ebp
mov ebp, esp
```

то аргументы обычно лежат так:

```text
[ebp+8]   first argument
[ebp+12]  second argument
[ebp+16]  third argument
[ebp+20]  fourth argument
```

Локальные переменные:

```text
[ebp-4]
[ebp-8]
[ebp-12]
```

Возвращаемое значение чаще всего в:

```text
eax
```

---

## 2. Шпаргалка паттернов

| ASM pattern | Возможный C-смысл |
|---|---|
| `[ebp+8]` | первый аргумент |
| `[ebp+12]` | второй аргумент |
| `[ebp-4]` | локальная переменная |
| `mov eax, [ebp+8]` | аргумент типа `int` или pointer |
| `movsx eax, byte [...]` | signed `char` -> `int` |
| `movzx eax, byte [...]` | unsigned `char` -> `int` |
| `movsx eax, word [...]` | signed `short` -> `int` |
| `movzx eax, word [...]` | unsigned `short` -> `int` |
| `mov [eax], edx` | запись по указателю |
| `lea eax, [...]` | вычисление адреса |
| `call f` | вызов функции |
| финальное значение в `eax` | return value |

Это не строгие доказательства, но очень сильные подсказки.

---

## 3. Как понять, что аргумент — указатель

Если значение аргумента используется как адрес, это почти наверняка pointer.

Пример:

```asm
mov eax, [ebp+8]
mov edx, [eax]
```

Здесь `[ebp+8]` загружается в `eax`, а потом используется `[eax]`.

Возможный C-смысл:

```cpp
int* p;
int value = *p;
```

Ещё пример:

```asm
mov eax, [ebp+8]
mov [eax], edx
```

Возможный C-смысл:

```cpp
*p = edx;
```

Если аргумент используется как база массива:

```asm
mov eax, [ebp+8]
mov edx, [ebp+12]
mov eax, [eax + 4*edx]
```

то `[ebp+8]` может быть `int* a`, а `[ebp+12]` — индекс `i`.

---

## 4. Как понять маленькие типы

Если аргумент или память читается через `byte` или `word`, это намёк на маленький тип.

```asm
movsx eax, byte [ebp+8]
```

Возможный тип:

```cpp
signed char
```

```asm
movzx eax, byte [ebp+8]
```

Возможный тип:

```cpp
unsigned char
```

```asm
movsx eax, word [ebp+8]
```

Возможный тип:

```cpp
short
```

```asm
movzx eax, word [ebp+8]
```

Возможный тип:

```cpp
unsigned short
```

Важно: в CDECL маленькие integer-типы часто передаются на стеке всё равно как 4-байтовые слоты, но код может читать нужную часть или расширять её.

---

## 5. Разбор главного примера

Фрагмент:

```asm
movsx edx, byte [ebp+12]
mov eax, [ebp+16]
mov [eax], edx
movsx eax, word [ebp+8]
mov edx, [ebp+20]
sub edx, eax
mov eax, edx
```

Разбираем медленно.

### Строка 1

```asm
movsx edx, byte [ebp+12]
```

`[ebp+12]` — второй аргумент.

Читаем `byte` и расширяем со знаком.

Значит, второй аргумент похож на:

```cpp
signed char d
```

Результат кладётся в `edx`.

### Строки 2–3

```asm
mov eax, [ebp+16]
mov [eax], edx
```

`[ebp+16]` — третий аргумент.

Его значение кладут в `eax`, а потом используют как адрес для записи.

Значит, третий аргумент похож на указатель:

```cpp
int* p
```

И действие:

```cpp
*p = d;
```

### Строка 4

```asm
movsx eax, word [ebp+8]
```

`[ebp+8]` — первый аргумент.

Читаем `word` и расширяем со знаком.

Похоже на:

```cpp
short c
```

### Строки 5–7

```asm
mov edx, [ebp+20]
sub edx, eax
mov eax, edx
```

`[ebp+20]` — четвёртый аргумент, вероятно `int x`.

Вычитаем из него `c`:

```cpp
x - c
```

Кладём в `eax`, значит возвращаем.

### Возможный C-код

```cpp
int f(short c, signed char d, int* p, int x)
{
    *p = d;
    return x - c;
}
```

---

## 6. Почему это не единственный C-код

Один и тот же asm может соответствовать разным исходникам.

Например:

```asm
mov eax, [ebp+8]
add eax, [ebp+12]
ret
```

Возможные C-варианты:

```cpp
int f(int a, int b) { return a + b; }
```

или:

```cpp
unsigned f(unsigned a, unsigned b) { return a + b; }
```

Для сложения битовый результат одинаков. Без контекста нельзя всегда точно сказать signed или unsigned.

Поэтому правильная формулировка:

> Возможный C-код такой-то.

А не:

> Единственный исходник был вот такой.

---

## 7. Как читать условия

Фрагмент:

```asm
mov eax, [ebp+8]
cmp eax, [ebp+12]
jle .else
mov eax, 1
jmp .end
.else:
mov eax, 0
.end:
ret
```

Читаем:

```asm
cmp eax, [ebp+12]
jle .else
```

Если `a <= b`, идём в else.

Если не идём, значит `a > b`, возвращаем 1.

Возможный C:

```cpp
int f(int a, int b)
{
    if (a > b)
        return 1;
    else
        return 0;
}
```

Или проще:

```cpp
return a > b;
```

---

## 8. Как читать цикл

Фрагмент:

```asm
xor eax, eax
xor ecx, ecx
.loop:
cmp ecx, [ebp+8]
jge .end
add eax, ecx
inc ecx
jmp .loop
.end:
ret
```

Роли:

```text
eax = sum
ecx = i
[ebp+8] = n
```

Цикл:

```cpp
int sum = 0;
for (int i = 0; i < n; ++i)
    sum += i;
return sum;
```

Признаки:

- `xor ecx, ecx` — `i = 0`;
- `cmp ecx, [ebp+8]`; `jge .end` — пока `i < n`;
- `inc ecx` — `++i`;
- `add eax, ecx` — накопление суммы.

---

## 9. Как читать массивы

Фрагмент:

```asm
mov edx, [ebp+8]
mov ecx, [ebp+12]
mov eax, [edx + 4*ecx]
ret
```

`[ebp+8]` используется как база адреса.

`[ebp+12]` используется как индекс.

`4*ecx` значит элемент размером 4 байта, вероятно `int`.

Возможный C:

```cpp
int f(int* a, int i)
{
    return a[i];
}
```

Если было бы:

```asm
movzx eax, byte [edx + ecx]
```

то возможный C:

```cpp
unsigned char* a;
return a[i];
```

# День 19. Структуры: поля — это смещения

## Опора на материалы ВШЭ

`Slides2026-0xB.pdf`: структуры, доступ к полям, массив внутри структуры, linked list, alignment, padding, layout структур в памяти.

## Зачем этот день

В C++ ты пишешь красиво:

```cpp
r->i
r->a[k]
r->p
```

А в памяти нет имён `i`, `a`, `p`. Там просто байты.

Компилятор знает, что поле `i` лежит со смещения 0, поле `a` со смещения 8, поле `p` со смещения 20. В asm это превращается в обычную адресацию:

```asm
[base + offset]
[base + index*scale + offset]
```

Сегодня мы учимся видеть структуру как layout в памяти.

---

## Главная мысль

Структура — это непрерывный блок памяти.

Поле — это фиксированное смещение внутри этого блока.

Padding — это пустые байты, которые компилятор вставляет для выравнивания.

---

## 1. Простая структура

C++:

```cpp
struct Point {
    int x;
    int y;
};
```

В IA-32 `int` занимает 4 байта, значит layout такой:

```text
offset:  0      4
       +------+------+
field: |  x   |  y   |
       +------+------+
```

Если `eax = address of Point`, то:

```asm
mov edx, [eax]      ; edx = point.x
mov edx, [eax + 4]  ; edx = point.y
```

В памяти нет строк “x” и “y”. Есть только смещения.

---

## 2. Структура с массивом и указателем

C++:

```cpp
struct rec {
    int i;
    int j;
    int a[3];
    rec* p;
};
```

В IA-32 pointer занимает 4 байта. Получаем layout:

```text
offset:  0      4      8      12     16     20
       +------+------+------+------+------+------+
field: |  i   |  j   | a[0] | a[1] | a[2] |  p   |
       +------+------+------+------+------+------+
```

Размер структуры:

```text
24 bytes
```

Если `edx = r`, то:

| C++ access | ASM address |
|---|---|
| `r->i` | `[edx]` or `[edx+0]` |
| `r->j` | `[edx+4]` |
| `r->a[0]` | `[edx+8]` |
| `r->a[1]` | `[edx+12]` |
| `r->a[k]` | `[edx+8+4*k]` |
| `r->p` | `[edx+20]` |

---

## 3. Разбор asm из структуры

```asm
mov eax, [edx]                 ; eax = r->i
mov [edx + 4*eax + 8], ecx     ; r->a[i] = val
mov edx, [edx + 20]            ; r = r->p
```

Разбираем.

### `mov eax, [edx]`

`edx` — база структуры.

`[edx]` — поле со смещения 0.

Значит:

```cpp
eax = r->i;
```

### `mov [edx + 4*eax + 8], ecx`

Адрес:

```text
edx + 8 + 4*eax
```

`8` — начало массива `a`.

`4*eax` — индекс элемента `int`.

Значит:

```cpp
r->a[i] = val;
```

если `eax = i`, `ecx = val`.

### `mov edx, [edx + 20]`

Поле со смещения 20 — `p`.

Значит:

```cpp
r = r->p;
```

Это похоже на переход к следующему узлу linked list.

---

## 4. Linked list на уровне asm

C++:

```cpp
while (r != nullptr) {
    sum += r->i;
    r = r->p;
}
```

ASM-shape:

```asm
xor eax, eax          ; sum = 0

.loop:
    test edx, edx     ; r == nullptr?
    je .end

    add eax, [edx]    ; sum += r->i
    mov edx, [edx+20] ; r = r->p
    jmp .loop

.end:
```

Здесь структура стала просто набором смещений:

```text
r->i = [edx]
r->p = [edx+20]
```

---

## 5. Padding и alignment

Иногда поля не лежат вплотную.

C++:

```cpp
struct S1 {
    char c;
    int x;
    char d;
};
```

Наивно можно подумать:

```text
1 + 4 + 1 = 6 bytes
```

Но компилятор обычно хочет, чтобы `int` лежал по адресу, кратному 4. Поэтому он вставляет padding.

Возможный layout IA-32:

```text
offset: 0   1   2   3   4          8   9  10  11
      +---+---+---+---+------------+---+---+---+---+
      | c | p | p | p |     x      | d | p | p | p |
      +---+---+---+---+------------+---+---+---+---+
```

`p` — padding byte.

Размер может стать 12 байт, а не 6.

---

## 6. Как порядок полей влияет на размер

Если переставить поля:

```cpp
struct S2 {
    int x;
    char c;
    char d;
};
```

Возможный layout:

```text
offset: 0          4   5   6   7
      +------------+---+---+---+---+
      |     x      | c | d | p | p |
      +------------+---+---+---+---+
```

Размер может быть 8 байт.

Поля те же, но структура компактнее.

Практический вывод:

> Порядок полей влияет на размер структуры из-за padding.

---

## 7. Почему нужен padding

Процессорам обычно удобнее читать данные с выровненных адресов.

Грубое правило:

```text
char  -> можно почти где угодно
short -> желательно адрес кратен 2
int   -> желательно адрес кратен 4
```

Это зависит от ABI и архитектуры, но для учебных задач достаточно понимать идею.

Компилятор вставляет padding, чтобы поля лежали по удобным адресам.

---

## 8. Array of structs

C++:

```cpp
rec arr[10];
```

Если `sizeof(rec) = 24`, то:

```text
&arr[k] = base + 24*k
```

Поле `arr[k].j`:

```text
base + 24*k + 4
```

Поле `arr[k].a[i]`:

```text
base + 24*k + 8 + 4*i
```

В asm масштаб `24*k` нельзя записать напрямую как `index*24`, потому что scale может быть только 1,2,4,8. Компилятор может использовать `imul` или несколько `lea`.

Пример:

```asm
mov eax, [k]
imul eax, 24
mov ecx, [base + eax + 4] ; arr[k].j
```

---

## 9. Union

`union` отличается от `struct` тем, что все поля начинаются с одного offset.

C++:

```cpp
union U {
    int x;
    char bytes[4];
};
```

Layout:

```text
offset 0:
+----------------+
| x / bytes[0..3]|
+----------------+
```

Размер union — размер самого большого поля с учётом выравнивания.

Это полезно для понимания того, что разные типы могут смотреть на одни и те же байты.

---

## 10. Reverse-паттерны структур

| ASM | Возможный C-смысл |
|---|---|
| `[eax]` | первое поле структуры |
| `[eax+4]` | второе `int`-поле или поле со смещением 4 |
| `[eax+20]` | поле со смещением 20, часто pointer в примерах |
| `[eax+4*ecx+8]` | массив `int` внутри структуры с offset 8 |
| `mov eax, [eax+offset]` | переход по pointer-полю |
| `imul index, sizeof(struct)` | доступ к array of structs |

Когда видишь постоянные смещения `0`, `4`, `8`, `20`, думай не только про массивы, но и про структуры.

---

## 11. Мини-челленджи

#### 1. Объясни адрес

```asm
[edx + 4*eax + 8]
```

если `edx = r`, `eax = i`, а у структуры есть `int a[3]` со смещения 8.

<details>
<summary>Ответ</summary>

Это `r->a[i]`.

</details>

#### 2. Почему `sizeof(S1)` не 6?

```cpp
struct S1 {
    char c;
    int x;
    char d;
};
```

<details>
<summary>Ответ</summary>

Из-за padding/alignment. Компилятор вставляет пустые байты, чтобы `int x` лежал по выровненному адресу и чтобы элементы массива структур тоже были выровнены.

</details>

#### 3. Что хранится в памяти: имена полей или байты?

<details>
<summary>Ответ</summary>

Байты. Имена полей существуют на уровне исходного кода и отладочной информации, но обычный машинный код работает со смещениями.

</details>

#### 4. Адрес `arr[k].j`

Если `sizeof(rec)=24`, `j` имеет offset 4, какой адрес?

<details>
<summary>Ответ</summary>

```text
base + 24*k + 4
```

</details>

#### 5. Что делает `mov edx, [edx+20]` в linked list?

<details>
<summary>Ответ</summary>

Переходит к следующему узлу: `r = r->p`, если поле `p` лежит со смещения 20.

</details>

## 12. Типовые ошибки

| Ошибка | Почему плохо |
|---|---|
| считать `sizeof(struct)` суммой полей | padding может увеличить размер |
| забыть offset поля | попадёшь не в то поле |
| путать массив структур и структуру с массивом | разные формулы адреса |
| думать, что имена полей есть в памяти | в машинном коде только смещения |
| забыть размер pointer в IA-32 | pointer = 4 bytes |
| записать scale 24 в адресации | x86 scale только 1,2,4,8 |
| не учитывать alignment | неверно посчитаешь layout |

# День 20. Что происходит до `main` и после него

## Опора на материалы ВШЭ

`Slides2026-0xC.pdf`: `_start`, `__libc_start_main`, initial stack, `argc/argv/envp`, `.init_array`, `.fini_array`, `objdump`, этапы сборки и запуска программы.

## Зачем этот день

В C++ кажется, что программа начинается с `main`.

```cpp
int main() {
    return 0;
}
```

Это удобная иллюзия. На самом деле до `main` уже произошло довольно много событий:

- ОС загрузила executable;
- подготовила память процесса;
- подготовила начальный стек;
- стартовый код вызвал libc;
- libc вызвала init-функции;
- и только потом управление дошло до твоего `main`.

Сегодня мы убираем последнюю большую магию: **что значит “программа запустилась”**.

---

## Главная мысль

`main` — это не первая инструкция процесса.

`main` — это пользовательская функция, которую вызывает стартовый код runtime.

Упрощённый путь:

```text
OS loader
   |
   v
_start
   |
   v
__libc_start_main(...)
   |
   v
constructors / init
   |
   v
main(argc, argv, envp)
   |
   v
destructors / fini
   |
   v
exit
```

Когда мы пишем:

```asm
global main
```

мы говорим не “вот первая инструкция процесса”, а:

> вот функция `main`, которую C runtime должен найти и вызвать.

---

## 1. Ещё раз: путь сборки

До запуска программа проходит несколько стадий.

```text
source code
   |
   | preprocessing / compilation
   v
assembly
   |
   | assembling
   v
object file (.o)
   |
   | linking
   v
executable
   |
   | loading
   v
process in memory
```

Для NASM:

```bash
nasm -f elf32 main.asm -o main.o
gcc -m32 -no-pie main.o -o main
./main
```

Стадии:

| Stage | Что получается |
|---|---|
| assembling | object file `.o` |
| linking | executable |
| loading | процесс в памяти |
| startup | `_start`, libc, init |
| user code | `main` |

---

## 2. Что делает loader

Loader — часть ОС, которая загружает программу в память.

Он примерно делает:

- читает executable file;
- создаёт адресное пространство процесса;
- размещает секции кода и данных;
- подключает динамические библиотеки;
- готовит стек;
- передаёт управление стартовой точке программы.

Упрощённая память процесса:

```text
higher addresses
+--------------------------+
| stack                    |
| grows downward           |
+--------------------------+
|                          |
| mmap / shared libraries  |
|                          |
+--------------------------+
| heap                     |
| grows upward             |
+--------------------------+
| .bss                     |
+--------------------------+
| .data                    |
+--------------------------+
| .rodata                  |
+--------------------------+
| .text                    |
+--------------------------+
lower addresses
```

Это не точная карта для каждой системы, но хорошая учебная модель.

---

## 3. Начальный стек

Когда программа только стартует, ОС кладёт на стек данные запуска.

Обычно там можно найти:

- `argc` — количество аргументов командной строки;
- `argv` — массив строк аргументов;
- `envp` — переменные окружения;
- служебные данные для dynamic loader.

Пример запуска:

```bash
./main hello 123
```

Тогда C видит:

```c
argc = 3
argv[0] = "./main"
argv[1] = "hello"
argv[2] = "123"
```

В `main` это приходит уже в удобном виде:

```c
int main(int argc, char** argv, char** envp)
```

Но до этого стартовый код должен забрать данные из начального стека и вызвать `main` по правилам ABI.

---

## 4. `_start`

`_start` — реальная стартовая точка обычной C-программы.

Ты обычно её не пишешь. Она приходит из startup files, которые подключает linker через `gcc`.

Именно поэтому мы линковали так:

```bash
gcc -m32 -no-pie main.o -o main
```

а не пытались вручную сразу сделать всё через `ld`.

`_start` подготавливает вызов libc и в итоге приводит к вызову `main`.

Если собрать совсем без libc и самому написать `_start`, можно сделать программу без `main`, но это уже отдельная низкоуровневая история.

---

## 5. `__libc_start_main`

`__libc_start_main` — функция libc, которая помогает запустить C-программу правильно.

Она отвечает за такие вещи:

- подготовить окружение C runtime;
- вызвать init-функции;
- вызвать твой `main`;
- обработать результат `main`;
- вызвать финализацию и `exit`.

То есть твой `main` находится внутри более большой схемы.

```text
_start -> __libc_start_main -> main -> exit
```

Для учебной цели не нужно знать все внутренности libc. Важно понимать, почему в дизассемблировании есть код до `main`.

---

## 6. `.init_array` и `.fini_array`

В C++ до `main` могут выполняться конструкторы глобальных объектов.

После `main` могут выполняться деструкторы.

Для этого используются специальные секции, например:

```text
.init_array
.fini_array
```

Упрощённо:

```text
.init_array  -> функции, которые надо вызвать до main
.fini_array  -> функции, которые надо вызвать после main / при exit
```

Пример C++:

```cpp
struct A {
    A()  { /* before main */ }
    ~A() { /* after main */ }
};

A global;

int main() {
    return 0;
}
```

Конструктор `global` выполнится до входа в `main`.

---

## 7. Что показывает `objdump`

Команды:

```bash
objdump -h main
```

Показывает секции.

```bash
objdump -d -M intel main
```

Показывает дизассемблирование.

```bash
objdump -s -j .data main
```

Показывает содержимое `.data`.

```bash
objdump -s -j .init_array main
objdump -s -j .fini_array main
```

Показывает содержимое init/fini секций, если они есть.

---

## 8. Почему в `objdump` много “лишнего”

Когда ты дизассемблируешь программу:

```bash
objdump -d -M intel main
```

ты видишь не только свой `main`.

Там могут быть:

- `_start`;
- PLT/GOT-код для динамических вызовов;
- startup/teardown код;
- служебные функции libc;
- выравнивание;
- куски, сгенерированные компилятором/линкером.

Это нормально.

Для начала ищи свою функцию:

```text
<main>:
```

В `less` удобно:

```text
/main
```

---

## 9. Почему `global main` работает

В NASM:

```asm
global main

main:
    xor eax, eax
    ret
```

`global main` экспортирует символ `main`, чтобы linker и C runtime могли его найти.

Если забыть `global main`, линковщик может сказать что-то вроде:

```text
undefined reference to main
```

Потому что startup-код ожидает, что пользовательская функция `main` существует.

---

## 10. Что если написать `_start` самому

Можно сделать программу без libc:

```asm
section .text
global _start

_start:
    mov eax, 1      ; sys_exit on old 32-bit Linux syscall ABI
    xor ebx, ebx    ; status 0
    int 0x80
```

Но в этом курсе основной путь другой:

```text
global main + gcc -m32 -no-pie + libc
```

Почему?

Потому что задачи используют `scanf`, `printf`, CDECL и обычное C-окружение. Нам выгоднее понимать `main`, а не вручную писать весь runtime.

---

## 11. Мини-челленджи

#### 1. Найди `_start`

Собери программу и выполни:

```bash
objdump -d -M intel main | less
```

Найди `<_start>`.

<details>
<summary>Подсказка</summary>

В `less` нажми `/`, введи `_start`, Enter.

</details>

#### 2. Найди `main`

Найди `<main>` в том же дизассемблировании.

<details>
<summary>Ответ</summary>

Там будет твой код: `xor eax,eax`, `ret` или инструкции из твоей программы.

</details>

#### 3. Почему `main` не первая инструкция?

<details>
<summary>Ответ</summary>

Потому что сначала управление получает стартовый код (`_start`), который подготавливает C runtime и вызывает `main`.

</details>

#### 4. Что такое `.init_array`?

<details>
<summary>Ответ</summary>

Секция с адресами функций, которые runtime вызывает до `main`, например для глобальных конструкторов C++.

</details>

#### 5. Почему мы используем `gcc -m32 -no-pie` для линковки?

<details>
<summary>Ответ</summary>

Потому что `gcc` как linker driver подключает нужный startup-код и libc, а `-m32` говорит линковать 32-битную программу.

</details>

## 12. Типовые ошибки

| Ошибка | Почему плохо |
|---|---|
| думать, что `main` — первая инструкция процесса | сначала работает loader/startup/runtime |
| искать только свой код в `objdump` и пугаться лишнего | дизассемблируется весь executable |

| думать, что constructors вызываются из `main` | глобальные constructors вызываются до `main` runtime-ом |

# День 21. Ошибки памяти и защиты

## Опора на материалы ВШЭ

`Slides2026-0xE.pdf`: выход за границы массива, buffer overflow, return-to-libc на уровне идеи, stack canary, ASLR, DEP/NX, FORTIFY_SOURCE, CFI/CET.

## Зачем этот день

В C++ ошибка памяти часто выглядит невинно:

```cpp
int a[3];
a[10] = 123;
```

Кажется: ну просто взяли “не тот элемент”.

Но на уровне asm и памяти элемента `a[10]` не существует. Есть только адрес, который оказался за пределами массива. По этому адресу может лежать что угодно:

- другая локальная переменная;
- сохранённый `ebp`;
- адрес возврата;
- данные другого объекта;
- служебная информация runtime.

Сегодня мы разбираем, почему ошибки памяти опасны и какие защиты пытаются их остановить.

---

## Важная рамка

Этот раздел нужен, чтобы понимать ошибки, защитные механизмы и смысл низкоуровневого кода.

Мы не пишем эксплойты и не разбираем пошаговую эксплуатацию. Для курса достаточно понимать:

```text
что может сломаться;
почему это связано со стеком;
какая защита что пытается предотвратить.
```

---

## Главная мысль

В памяти рядом могут лежать и данные, и служебные значения управления программой.

Если программа пишет за пределы буфера, она может испортить не только “чужие данные”, но и информацию, от которой зависит управление выполнением.

```text
ошибка индекса -> запись не туда -> повреждение памяти -> странное поведение / crash / security bug
```

---

## 1. Почему `a[10]` опасен

C++:

```cpp
int a[3];
a[10] = 123;
```

Если `a` лежит на стеке, рядом с ним могут быть другие данные фрейма.

Упрощённая картинка:

```text
higher addresses
+------------------+
| return address   |
+------------------+
| saved ebp        |
+------------------+
| local variable   |
+------------------+
| a[2]             |
+------------------+
| a[1]             |
+------------------+
| a[0]             |
+------------------+
lower addresses
```

`a[0]`, `a[1]`, `a[2]` — нормальные элементы.

`a[3]`, `a[4]`, ... — это уже не элементы массива. Это просто память рядом.

Что именно там окажется, зависит от компилятора, оптимизаций, ABI и защит.

---

## 2. Undefined behavior

В C/C++ выход за границы массива — undefined behavior.

Это значит не “программа обязана упасть”.

Это значит:

```text
язык больше не обещает никакого нормального поведения.
```

Возможные варианты:

- программа работает “как будто нормально”;
- печатает мусор;
- падает;
- ломает соседние переменные;
- работает по-разному на разных компиляторах;
- ломается только с оптимизациями;
- создаёт уязвимость.

Самое неприятное: если сегодня “работает”, это не значит, что код правильный.

---

## 3. Buffer overflow на уровне идеи

Buffer overflow — это запись за пределы буфера.

Пример:

```c
char buf[16];
// слишком длинный ввод записался в buf
```

Упрощённый стек:

```text
higher addresses
+------------------+
| return address   |
+------------------+
| saved ebp        |
+------------------+
| local buffer     |
| buf[0..15]       |
+------------------+
lower addresses
```

Если запись выходит за `buf`, она может дойти до сохранённого `ebp` или address return.

Почему это страшно?

`ret` берёт адрес возврата со стека. Если адрес возврата испорчен, управление может уйти не туда.

---

## 4. Stack canary

Stack canary — защитное значение между локальным буфером и служебными данными фрейма.

```text
higher addresses
+------------------+
| return address   |
+------------------+
| saved ebp        |
+------------------+
| canary           |
+------------------+
| local buffer     |
+------------------+
lower addresses
```

Идея:

1. при входе в функцию положить canary в стек;
2. перед выходом проверить, не изменился ли он;
3. если изменился — вероятно, буфер переписал память выше себя;
4. аварийно завершить программу.

Псевдологика:

```text
on entry:
    stack_canary = secret_value

before return:
    if stack_canary != secret_value:
        abort
```

Canary не “исправляет” ошибку. Он пытается её обнаружить до `ret`.

---

## 5. ASLR

ASLR = Address Space Layout Randomization.

Идея: каждый запуск раскладывать важные области памяти по разным адресам.

Без ASLR:

```text
library address = same every run
stack address   = same every run
```

С ASLR:

```text
library address = changes
stack address   = changes
heap address    = changes
```

Это усложняет атаки, которые зависят от знания точных адресов.

Но ASLR не исправляет сам bug. Если в программе есть выход за границы, он всё ещё есть.

---

## 6. DEP / NX

DEP/NX запрещает исполнять страницы памяти, предназначенные для данных.

Идея:

```text
code pages: executable
data/stack/heap pages: not executable
```

Если кто-то пытается выполнить байты из стека как код, процессор/ОС должны запретить это.

DEP/NX отвечает на идею:

> данные не должны становиться кодом.

Но это тоже не исправляет buffer overflow. Это только усложняет превращение ошибки в выполнение произвольного кода.

---

## 7. FORTIFY_SOURCE

`FORTIFY_SOURCE` — набор дополнительных проверок для некоторых функций libc, когда компилятор может понять размер буфера.

Например, для опасных операций копирования строк/памяти runtime может добавить проверку:

```text
не копируем ли мы больше, чем размер буфера?
```

Это не универсальная защита от всех ошибок памяти. Но она может поймать часть типичных ошибок раньше.

---

## 8. CFI / CET на уровне идеи

CFI = Control-Flow Integrity.

Идея: программа должна переходить только туда, куда разрешено её нормальной структурой.

CET — аппаратные механизмы Intel для усиления защиты control flow, например shadow stack и indirect branch tracking.

Для курса достаточно понимать:

```text
canary -> пытается заметить порчу стека;
ASLR   -> скрывает точные адреса;
DEP/NX -> запрещает исполнять данные;
CFI/CET -> ограничивает допустимые переходы управления.
```

---

## 9. Return-to-libc на уровне идеи

DEP/NX запрещает исполнять код на стеке. Но в процессе уже есть готовый код библиотек.

Return-to-libc — историческая идея атаки: вместо выполнения кода из стека попытаться передать управление уже существующей функции библиотеки.

Для курса важно только это:

```text
защиты закрывают одни классы атак,
но ошибки памяти всё равно опасны,
потому что управление программой можно пытаться перенаправлять разными способами.
```

Не нужно изучать практические цепочки вызовов. Нужна концептуальная связь: стек, return address, библиотеки, control flow.

---

## 10. Почему это важно обычному C++-программисту

Потому что многие “странные баги” становятся понятными:

```cpp
int a[3];
int x = 10;
a[3] = 999;
```

Если `x` лежал рядом, он мог внезапно измениться.

Или:

```cpp
char buf[8];
scanf("%s", buf);
```

Если ввод длиннее 7 символов плюс ноль-терминатор, запись выйдет за пределы буфера.

Ассемблер помогает не магически “защититься”, а увидеть реальную причину: адреса, стек, соседние данные.

---

# День 22. Вещественные числа: почему `0.1` не точное

## Опора на материалы ВШЭ

`Slides2026-0xF.pdf`, `Slides2026-15.pdf`: двоичные дроби, floating point, нормализованные и денормализованные числа, `+0/-0`, `Inf`, `NaN`, округление и ограничения представления.

## Зачем этот день

С целыми числами всё было относительно честно:

```text
32 бита -> одно из 2^32 возможных значений
```

Да, signed/unsigned могут читать эти биты по-разному, но сами целые значения в диапазоне представлены точно.

С вещественными числами иначе. Многие привычные десятичные дроби нельзя точно записать конечным числом двоичных битов.

Например:

```cpp
double x = 0.1;
```

обычно хранит не ровно `0.1`, а ближайшее представимое значение.

Сегодня разбираем, почему так происходит и как floating point устроен на уровне идеи.

---

## Главная мысль

Floating point — это приближённое представление числа в форме:

```text
sign * mantissa * 2^exponent
```

У числа есть:

- знак;
- порядок / exponent;
- дробная часть / fraction;
- специальные случаи: нули, денормалы, бесконечности, NaN.

---

## 1. Двоичные дроби

В десятичной системе:

```text
123.45 = 1*100 + 2*10 + 3*1 + 4/10 + 5/100
```

В двоичной системе дробная часть использует степени 2:

```text
0.1₂ = 1/2
0.01₂ = 1/4
0.001₂ = 1/8
```

Пример:

```text
5.75 decimal
```

Целая часть:

```text
5 = 101₂
```

Дробная часть:

```text
0.75 = 1/2 + 1/4 = 0.11₂
```

Итого:

```text
5.75₁₀ = 101.11₂
```

---

## 2. Почему `0.1` не точное

`0.1` в десятичной системе — это:

```text
1/10
```

А:

```text
10 = 2 * 5
```

Конечные двоичные дроби имеют знаменатель степени двойки:

```text
1/2, 1/4, 1/8, 1/16, ...
```

Если в знаменателе есть множитель 5, дробь в binary обычно становится бесконечной периодической.

```text
0.1₁₀ = 0.00011001100110011...₂
```

Поэтому компьютер хранит ближайшее число, которое помещается в доступные биты.

---

## 3. Почему это важно

В C++:

```cpp
double a = 0.1;
double b = 0.2;
double c = 0.3;
```

Не стоит уверенно писать:

```cpp
if (a + b == c)
```

Потому что `a`, `b`, `c` могут быть приближениями.

Обычно сравнивают с погрешностью:

```cpp
abs((a + b) - c) < eps
```

Ассемблер здесь не делает магию точности. Он просто выполняет операции над представимыми floating point значениями.

---

## 4. Общая идея scientific notation

В десятичной записи:

```text
12345 = 1.2345 * 10^4
```

В двоичной floating point идея похожая:

```text
value = mantissa * 2^exponent
```

Например:

```text
101.11₂ = 1.0111₂ * 2^2
```

Потому что мы перенесли точку на 2 позиции влево.

---

## 5. Layout `float`

Обычный 32-битный `float` можно представить так:

```text
31     30          23 22                    0
+--------+------------+----------------------+
| sign   | exponent   | fraction             |
+--------+------------+----------------------+
  1 bit     8 bits           23 bits
```

| Поле | Зачем |
|---|---|
| `sign` | знак числа |
| `exponent` | порядок, степень двойки с bias |
| `fraction` | дробная часть мантиссы |

Упрощённая формула:

```text
(-1)^sign * mantissa * 2^exponent
```

Точная IEEE-формула использует bias и скрытую единицу для нормализованных чисел, но на первом проходе важна идея: число хранится не как десятичная строка, а как знак + масштаб + значащие биты.

---

## 6. Нормализованные числа

Для обычных нормализованных чисел мантисса имеет вид:

```text
1.xxxxx₂
```

Эта первая `1` обычно не хранится явно. Её называют hidden bit / implicit leading one.

Почему можно не хранить?

Потому что у нормализованного ненулевого двоичного числа первая значащая цифра всегда `1`.

Пример:

```text
101.11₂ = 1.0111₂ * 2^2
```

Мантисса начинается с `1.`.

---

## 7. Денормализованные числа

Денормализованные числа нужны для очень маленьких значений около нуля.

Идея:

```text
когда нормализованного exponent уже не хватает,
мы разрешаем числа без скрытой ведущей 1.
```

Они помогают сделать переход к нулю более плавным.

Для курса достаточно понимать:

- normal — обычные числа;
- denormal/subnormal — очень маленькие числа около нуля;
- они имеют отдельный encoding.

---

## 8. Специальные значения

Floating point хранит не только обычные числа.

| exponent | fraction | Meaning |
|---|---|---|
| all zero | zero | `+0` / `-0` |
| all zero | non-zero | denormalized/subnormal |
| normal | any | normalized number |
| all ones | zero | `+Inf` / `-Inf` |
| all ones | non-zero | `NaN` |

### `+0` и `-0`

У floating point есть положительный и отрицательный ноль.

Обычно они сравниваются как равные, но в некоторых операциях знак нуля может проявляться.

### Infinity

`Inf` появляется, например, при overflow или делении ненулевого числа на ноль в floating point модели.

### NaN

`NaN` = Not a Number.

Это не “очень большое число”. Это специальное значение для некорректных результатов:

```text
0.0 / 0.0
sqrt(-1.0) в вещественной арифметике
Inf - Inf
```

---

## 9. Округление

Так как битов конечное число, результат операции часто приходится округлять.

Например, если точный результат требует больше битов мантиссы, чем есть, процессор выбирает ближайшее представимое значение по текущему режиму округления.

Типовая мысль:

```text
floating point arithmetic is not real-number arithmetic
```

Она похожа на вещественную математику, но не равна ей идеально.

---

## 10. Почему порядок операций важен

В вещественной математике:

```text
(a + b) + c = a + (b + c)
```

В floating point это может быть не совсем так из-за округления.

Примерная идея:

```cpp
double a = 1e20;
double b = -1e20;
double c = 3.14;
```

```cpp
(a + b) + c = 3.14
```

а:

```cpp
a + (b + c)
```

может потерять `c` при сложении очень большого и маленького числа.

Для asm это важно потому, что низкоуровневый порядок операций может влиять на точность.

---

Следующий день будет про x87 FPU.

Там floating point будет не в `eax/ebx`, а в отдельном стековом наборе регистров:

```text

```

Сегодня нужно понять сами числа. Завтра — как x87 их кладёт на стек и считает.

# День 23. x87: вещественные числа как стек

## Опора на материалы ВШЭ

`Slides2026-0x10.pdf`: x87 FPU, `FINIT`, регистры `st0..st7`, control/status/tag word, `fld`, `fst`, `fstp`, `faddp`, `fsubp`, `fmulp`, `fdivp`, печать через `printf("%f")`, связь со стековой моделью и обратной польской записью.

## Зачем этот день

До сих пор мы работали в основном с целыми числами в регистрах:

```text
eax, ebx, ecx, edx
```

Но вещественные числа исторически обрабатывались отдельным блоком — x87 FPU.

x87 не похож на обычные регистры общего назначения. Он работает как стек:

```text
положили число;
положили второе;
операция взяла верхние элементы;
результат остался на вершине.
```

Сначала это непривычно. Но если думать как об обратной польской записи, становится нормально.

---

## Главная мысль

x87 — стековая машина для floating point.

```text
fld   -> push floating value
faddp -> add top values and pop
fstp  -> store and pop
```

Для `printf("%f")` нужно передавать `double`, то есть `qword`, даже если исходное число было `float`.

---

## 1. x87 stack

x87 имеет стек из 8 регистров:

```text
+-----------+
|   st(7)   |
+-----------+
|   st(6)   |
+-----------+
|   st(5)   |
+-----------+
|   st(4)   |
+-----------+
|   st(3)   |
+-----------+
|   st(2)   |
+-----------+
|   st(1)   |
+-----------+
|   st(0)   | <- top
+-----------+
```

`st(0)` — вершина стека.

После `fld x` значение оказывается в `st(0)`.

После второго `fld y`:

```text
st(0) = y
st(1) = x
```

---

## 2. `finit`

```asm
finit
```

Инициализирует x87 FPU: приводит его состояние к нормальному начальному виду.

В маленьких учебных программах `finit` часто ставят в начале работы с x87, чтобы не зависеть от старого состояния.

---

## 3. Загрузка и сохранение

### `fld`

```asm
fld dword [x]
```

Читает floating point значение из памяти и кладёт на вершину x87-стека.

```text
before:
empty

after fld [x]:
st(0) = x
```

Можно загружать разные размеры:

```asm
fld dword [floatValue]   ; 32-bit float
fld qword [doubleValue]  ; 64-bit double
```

### `fst`

```asm
fst dword [x]
```

Сохраняет `st(0)` в память, но не снимает его со стека.

### `fstp`

```asm
fstp dword [x]
```

Сохраняет `st(0)` в память и делает pop.

То есть:

```text
fst  -> store
fstp -> store + pop
```

---

## 4. Сложение через x87

Пусть есть:

```asm
section .data
    x dd 1.5
    y dd 2.25
    z dd 0.0
```

Код:

```asm
finit
fld dword [x]
fld dword [y]
faddp
fstp dword [z]
```

Разберём по шагам.

После:

```asm
fld dword [x]
```

```text
st(0) = x
```

После:

```asm
fld dword [y]
```

```text
st(0) = y
st(1) = x
```

После:

```asm
faddp
```

x87 складывает верхние элементы и снимает один:

```text
st(0) = x + y
```

После:

```asm
fstp dword [z]
```

```text
z = x + y
stack is empty again
```

---

## 5. Арифметические команды

| Instruction | Meaning |
|---|---|
| `faddp` | сложить верхние значения и pop |
| `fsubp` | вычесть и pop |
| `fmulp` | умножить и pop |
| `fdivp` | разделить и pop |

В учебной модели удобно думать так:

```text
fld a
fld b
operation
```

похоже на:

```text
a b operation
```

в обратной польской записи.

---

## 6. Порядок для `fsubp` и `fdivp`

Сложение и умножение коммутативны: порядок не так страшен.

А вот вычитание и деление требуют внимания. Безопаснее писать явную форму, где видно оба операнда.

### Шаблон `a - b`

```asm
fld dword [a]
fld dword [b]
fsubp st1, st0      ; st1 = st1 - st0, pop
```

После этого:

```text
st(0) = a - b
```

### Шаблон `a / b`

```asm
fld dword [a]
fld dword [b]
fdivp st1, st0      ; st1 = st1 / st0, pop
```

После этого:

```text
st(0) = a / b
```

Практический тест:

```text
a = 10
b = 2

a - b = 8
a / b = 5
```

Если получил `-8` или `0.2`, порядок перепутан.

## 7. Печать через `printf("%f")`

В C variadic-функции вроде `printf` получают `float` как `double`.

То есть:

```c
printf("%f", value);
```

ожидает 8 байт `double`.

В NASM это значит: перед `printf` нужно положить на стек `qword`.

Пример:

```asm
section .data
    fmt db "%f", 10, 0
    x dd 1.5
    y dd 2.25

section .text
    extern printf
    global main

main:
    finit
    fld dword [x]
    fld dword [y]
    faddp

    sub esp, 8
    fstp qword [esp]
    push fmt
    call printf
    add esp, 12

    xor eax, eax
    ret
```

Разбор:

```asm
sub esp, 8
fstp qword [esp]
```

Выделили 8 байт на стеке и сохранили туда `double`.

```asm
push fmt
call printf
add esp, 12
```

Аргументы `printf`:

```text
format pointer -> 4 bytes
floating value -> 8 bytes
итого 12 bytes
```

---

## 8. Типовая ошибка с `%f`

Плохо:

```asm
fstp dword [esp+4]
```

если дальше:

```asm
call printf
```

с форматом:

```c
"%f"
```

Почему плохо?

`%f` ждёт `double` — 8 байт. А `dword` — только 4 байта `float`. `printf` прочитает не те байты и напечатает мусор.

Правильно:

```asm
fstp qword [somewhere]
```

---

## 9. x87 status/control/tag word на уровне идеи

В x87 есть не только регистры `st(0)..st(7)`, но и служебные слова состояния.

| Word | Идея |
|---|---|
| control word | режимы округления, маски исключений |
| status word | состояние FPU, исключения, condition flags |
| tag word | какие регистры стека заняты/пусты |

Для задач обычно не нужно вручную ими управлять. Но важно знать: x87 — не просто “8 double-регистров”, это отдельная подсистема со своим состоянием.

---

## 10. Связь с обратной польской записью

Выражение:

```text
(a + b) * c
```

В обратной польской записи:

```text
a b + c *
```

x87-идея:

```asm
fld a
fld b
faddp
fld c
fmulp
```

То есть сначала кладём операнды, потом применяем операцию к верхушке стека.

Это полезная модель для сложных выражений.

#### 1. Нарисуй x87 stack

После:

# День 24. C++-объект как `struct` с секретным указателем

## Опора на материалы ВШЭ

`Slides2026-0xD.pdf`: объект как структура, служебные поля, `vptr`, VMT, RTTI, virtual methods, hidden `this`, `thiscall` и низкоуровневая модель C++-объектов.

## Зачем этот день

C++ выглядит высокоуровнево:

```cpp
obj.field
obj.method()
obj.virtualMethod()
```

Но процессор не знает “методов”, “классов” и “виртуальности”. В памяти объект всё равно похож на блок байтов. Методы — это функции. Поля — смещения. Виртуальные методы — косвенные вызовы через таблицу.

Сегодня мы не пишем сложный C++ ABI руками. Мы учимся видеть идею:

```text
object = struct-like layout + sometimes service pointers
method = function with hidden this
virtual call = call through function pointer table
```

---

## Главная мысль

C++-объект на низком уровне похож на структуру.

Если есть виртуальные методы, в объекте обычно появляется скрытый указатель `vptr`, который ведёт к таблице виртуальных методов.

```text
Object:

+------------------+
| vptr             | ---> +---------------------+
+------------------+      | virtual method #0   |
| field1           |      +---------------------+
+------------------+      | virtual method #1   |
| field2           |      +---------------------+
+------------------+
```

---

## 1. Обычный объект без virtual

C++:

```cpp
struct Point {
    int x;
    int y;

    int sum() {
        return x + y;
    }
};
```

Данные объекта похожи на структуру:

```text
offset:  0      4
       +------+------+
field: |  x   |  y   |
       +------+------+
```

Метод `sum` не лежит внутри каждого объекта как отдельный код. Код метода существует отдельно, как функция.

Объект хранит поля, а не копии методов.

---

## 2. Hidden `this`

Когда ты пишешь:

```cpp
p.sum()
```

на низком уровне это похоже на вызов функции с дополнительным скрытым аргументом:

```cpp
Point_sum(&p)
```

`this` — это адрес текущего объекта.

Метод:

```cpp
int Point::sum() {
    return x + y;
}
```

можно мысленно представить так:

```cpp
int Point_sum(Point* this) {
    return this->x + this->y;
}
```

В asm это превращается в доступы по смещениям от адреса объекта:

```asm
mov eax, [this + 0]  ; x
add eax, [this + 4]  ; y
```

Конкретно где передаётся `this`, зависит от соглашения вызова и компилятора. В 32-битных C++ ABI часто встречается `thiscall`, где `this` может передаваться через регистр, например `ecx`, но детали ABI лучше уточнять под платформу.

---

## 3. Поля — это offsets

C++:

```cpp
class A {
public:
    int x;
    int y;
};
```

Если `eax = &obj`, то:

```asm
mov edx, [eax]      ; obj.x
mov edx, [eax + 4]  ; obj.y
```

Никакого имени `x` в обычной памяти объекта нет.

Имя `x` использовалось компилятором, чтобы выбрать offset `0`.

Имя `y` использовалось компилятором, чтобы выбрать offset `4`.

---

## 4. Virtual methods и `vptr`

Если в классе есть виртуальные методы:

```cpp
struct Base {
    virtual int f();
    int x;
};
```

объекту обычно нужен способ понять, какую именно реализацию `f` вызвать.

Для этого используется таблица виртуальных методов.

Упрощённо:

```text
Base object:

+------------------+
| vptr             | ---> VMT / vtable
+------------------+
| x                |
+------------------+
```

`vptr` — указатель на таблицу.

Таблица содержит адреса виртуальных функций.

```text
vtable:
+---------------------+
| &Base::f            |
+---------------------+
| &Base::otherVirtual |
+---------------------+
```

---

## 5. Virtual call

C++:

```cpp
Base* p = ...;
p->f();
```

Если `f` виртуальная, компилятор не может просто написать:

```asm
call Base_f
```

Потому что реальный объект может быть наследником:

```cpp
struct Derived : Base {
    int f() override;
};
```

Тогда нужно вызвать `Derived::f`, если объект на самом деле `Derived`.

Упрощённый asm-shape:

```asm
mov eax, [p]        ; eax = object pointer, условно
mov edx, [eax]      ; edx = vptr
call dword [edx]    ; call first virtual method
```

Для метода не на первой позиции таблицы будет смещение:

```asm
call dword [edx + 4]
```

В реальном коде будет ещё передача `this` и ABI-детали.

---

## 6. Direct call vs indirect call

Обычный вызов функции:

```asm
call some_function
```

Адрес функции известен прямо в коде.

Виртуальный вызов:

```asm
call dword [edx + offset]
```

Адрес функции читается из памяти, из таблицы.

| Вызов | Как выбирается адрес |
|---|---|
| direct call | адрес функции известен заранее |
| indirect call | адрес функции лежит в регистре/памяти |
| virtual call | адрес берётся из vtable объекта |

---

## 7. Inheritance на уровне идеи

C++:

```cpp
struct Base {
    int a;
};

struct Derived : Base {
    int b;
};
```

Упрощённо объект `Derived` может начинаться с части `Base`:

```text
Derived object:

+------------------+
| Base::a          |
+------------------+
| Derived::b       |
+------------------+
```

Поэтому указатель на `Derived` часто можно рассматривать как указатель на `Base`-часть объекта.

Для сложного наследования, multiple inheritance и virtual inheritance layout становится сложнее. Для этого курса достаточно базовой идеи: объект — это layout, а наследование влияет на расположение полей и служебных указателей.

---

## 8. RTTI

RTTI = runtime type information.

Это служебная информация, которая помогает во время выполнения узнавать тип объекта, например для:

```cpp
dynamic_cast

typeid
```

RTTI часто связана с таблицами виртуальных методов и служебными структурами компилятора.

Для курса достаточно понимать:

```text
RTTI — не магия языка, а дополнительные данные runtime/ABI.
```

---

## 9. Почему это важно для asm

Если ты увидел:

```asm
mov eax, [ecx]
call dword [eax+8]
```

это может быть виртуальный вызов:

```text
ecx = this
eax = vptr
[eax+8] = address of virtual method
```

Если ты увидел доступы:

```asm
mov eax, [ecx+4]
add eax, [ecx+8]
```

это может быть метод, который читает поля объекта через `this`.

---

## 10. Что где хранится

| C++ feature | Low-level idea |
|---|---|
| field | bytes at fixed offset |
| object | struct-like memory block |
| non-virtual method | ordinary function with hidden `this` |
| virtual method | function pointer selected from vtable |
| `this` | pointer to current object |
| inheritance | object layout includes base part |
| RTTI | runtime metadata |
| method name | not stored in each object |

#### 1. Нарисуй объект

Класс:

```cpp

    int y;

```

Нарисуй возможный layout.

<details>
<summary>Ответ</summary>

Упрощённо:

```text

+------------------+

+------------------+

+------------------+
```

</details>

#### 2. Что такое hidden `this`?

<details>
<summary>Ответ</summary>

</details>

#### 3. Чем virtual call отличается от прямого `call label`?

<details>
<summary>Ответ</summary>

При virtual call адрес функции берётся из таблицы виртуальных методов объекта, а при direct call адрес известен прямо в инструкции.

<details>

#### 5. Что может означать `mov eax, [ecx+4]` внутри метода?

<details>

</details>

## 12. Типовые ошибки

| Ошибка | Почему плохо |
|---|---|
| думать, что объект хранит копии методов | методы — код отдельно, объект хранит данные |
| считать `vptr` обычным видимым полем C++ | это служебная деталь ABI/реализации |
| забывать hidden `this` | методы не поймут, с каким объектом работать |
| думать, что virtual call — обычный `call label` | он идёт через таблицу/указатель |
| переносить layout между компиляторами без проверки | C++ ABI и layout могут отличаться |
| слишком буквально воспринимать упрощённые схемы | реальный C++ object model сложнее |

### 01-7. Упаковка вектора

Формула:

```cpp
x = a | (b << 8) | (c << 16) | (d << 24);
```

Картинка:

```text
31..24      23..16      15..8       7..0
+-----------+-----------+-----------+-----------+
|     d     |     c     |     b     |     a     |
+-----------+-----------+-----------+-----------+
```

Команды:

```asm
shl
or
and ; если надо ограничить байт
```

Проверка:

```text
1 2 3 4 -> 0x04030201
```

### 01-8. Masked merge

Формула:

```cpp
d = (a & c) | (b & ~c);
```

Крайние тесты:

```text
c = 0          -> answer = b
c = FFFFFFFFh  -> answer = a
```

### 01-9. Модуль числа без переходов

Формула:

```cpp
uint32_t ux = static_cast<uint32_t>(x);
uint32_t mask = 0u - (ux >> 31);
uint32_t ans = (ux ^ mask) - mask;
```

Так C++-запись точно воспроизводит 32-битную маску `0/FFFFFFFFh`, которую в NASM даёт `sar reg, 31`. Для `INT32_MIN` битовый результат равен `0x80000000`, но положительное значение `2147483648` не помещается в `int32_t`; это нужно учитывать в условии задачи и формате вывода.

NASM:

```asm
mov eax, [x]
mov edx, eax
sar edx, 31
xor eax, edx
sub eax, edx
```

Главная ловушка:

```text
нужен sar, не shr
```

### 01-10. Год на Пандоре

Формула:

```cpp
before = month - 1;
answer = before * 41 + before / 2 + day;
```

NASM:

```asm
mov eax, [month]
sub eax, 1
mov ecx, eax
imul eax, 41
shr ecx, 1
add eax, ecx
add eax, [day]
```

---

::: tip Про вывод битовых ответов
Если задача битовая и ответ проверяется как unsigned 32-bit, используй `%u`, а не `%d`:

```asm
fmtOut db "%u", 10, 0
```

Для signed-арифметики оставляем `%d`.
:::

### Часть B. Прочитать код

#### B1. `cmp` и signed/unsigned

```asm
cmp eax, ebx
jl .L1
jb .L2
```

Объясни разницу `jl` и `jb`.

<details>
<summary>Ответ</summary>

`jl` — signed `<`, смотрит на signed-отношение через `SF/OF`.

`jb` — unsigned `<`, смотрит на borrow/carry через `CF`.

Для одних и тех же битов результат может отличаться.

</details>

#### B2. `test`

```asm
test eax, eax
je .zero
```

Что это значит?

<details>
<summary>Ответ</summary>

Проверка `eax == 0`. `test eax,eax` обновляет флаги как `eax & eax`, не меняя `eax`.

</details>

#### B3. Адресация

```asm
lea eax, [edx + 4*ecx + 8]
```

Что делает эта строка?

<details>
<summary>Ответ</summary>

Считает адрес/выражение `edx + 4*ecx + 8` и кладёт в `eax`. Память не читает.

</details>

#### B4. Массив

```asm
mov eax, [edx + 4*ecx]
```

Возможный C-смысл?

<details>
<summary>Ответ</summary>

Если `edx` — база `int`-массива, `ecx` — индекс, то:

```cpp
eax = a[i];
```

</details>

#### C1. Нарисуй фрейм

Функция имеет два аргумента и две локальные `int`-переменные. Нарисуй расположение относительно `ebp`.

Результат в `eax`.

</details>

### Часть D. Reverse engineering

#### D1. Восстанови смысл

```asm
mov eax, [ebp+8]
add eax, [ebp+12]
ret
```

<details>
<summary>Ответ</summary>

Возможный C-смысл:

```cpp
int f(int a, int b)
{
    return a + b;
}
```

</details>

#### D2. Указатель

```asm
mov eax, [ebp+8]
mov edx, [ebp+12]
mov [eax], edx
ret
```

<details>
<summary>Ответ</summary>

Первый аргумент похож на указатель:

```cpp
void f(int* p, int x)
{
    *p = x;
}
```

Точный тип может зависеть от контекста.

</details>

#### D3. Маленький тип

```asm
movsx eax, byte [ebp+8]
ret
```

<details>
<summary>Ответ</summary>

Первый аргумент/значение читается как signed byte, возможный тип `signed char`, возвращается как `int`.

</details>

### Часть E. Объяснить словами

#### E1. Что делает canary?

<details>
<summary>Ответ</summary>

Canary — защитное значение между локальным буфером и служебными данными фрейма. Перед возвратом функция проверяет, не изменился ли canary. Если изменился — вероятно, было переполнение буфера.

</details>

#### E2. Почему `printf("%f")` ждёт `qword`?

<details>
<summary>Ответ</summary>

В variadic C-функциях `float` продвигается до `double`, а `double` занимает 8 байт. Поэтому для `%f` нужно передавать `qword`.

</details>

#### E3. Что такое hidden `this`?

<details>
<summary>Ответ</summary>

Это скрытый параметр метода: адрес объекта, для которого вызван метод.

</details>

## 7. Финальный принцип

Ассемблер становится понятным не тогда, когда ты выучил 100 команд.

Он становится понятным, когда ты видишь движение данных:

```text
memory -> register -> operation -> flags / memory / stack
```

И можешь честно ответить на вопросы:

```text
где лежит значение?
какого оно размера?
это адрес или данные?
какая инструкция меняет флаги?
куда прыгнет управление?
кто чистит стек?
что будет в eax перед ret?
```

Если эти вопросы стали привычными, ты уже не “боишься NASM”, а читаешь его как нормальный низкоуровневый язык.
