## За 30 секунд

- Объект структуры занимает непрерывную область памяти.
- Поле находится по постоянному смещению от адреса объекта.
- Выравнивание может добавлять заполняющие байты между полями и в конце объекта.
- Размер структуры обычно кратен её требованию выравнивания.
- Массив структур использует шаг `sizeof(struct)`.
- Связный список переходит к следующему узлу через поле-указатель.
- Размер поля определяет число читаемых байтов, а signedness отдельно определяет `movsx` или `movzx`.

## Минимум после главы

После главы ты должен уметь:

- вычислить смещения простых полей;
- объяснить появление заполняющих байтов;
- оценить `sizeof` в явно заданной учебной ABI-модели;
- написать доступ к полю через указатель;
- выбрать знаковое или нулевое расширение по объявленному типу поля;
- различить массив структур и связный список;
- отделить типичное расположение от гарантии языка C++.

## Главная модель

```text
field_address = object_address + field_offset
```

Имена полей не хранятся внутри каждого объекта. Компилятор заменяет их числовыми смещениями.

Центральный инвариант:

> Смещение поля вычисляется от начала того же объекта; число читаемых байтов задаётся размером поля; способ расширения задаётся signedness; точное расположение зависит от типов, выравнивания, ABI и параметров упаковки.

---

## Простая структура

```cpp
struct Point {
    int x;
    int y;
};
```

В учебной IA-32-модели `int` имеет размер 4 и выравнивание 4:

```text
offset 0  → x
offset 4  → y
sizeof    → 8
```

Если `eax` хранит адрес объекта:

```asm
mov edx, [eax]       ; x
mov ecx, [eax+4]     ; y
```

---

## Зачем нужны заполняющие байты

```cpp
struct Item {
    unsigned char tag;
    int value;
};
```

Без выравнивания размеры дали бы 5 байт. Но в типичной учебной модели `int` должен начинаться по адресу, кратному 4:

```text
offset 0  → tag, 1 byte
offset 1  → padding
offset 2  → padding
offset 3  → padding
offset 4  → value, 4 bytes
sizeof    → 8
```

Заполняющие байты не являются отдельными полями программы. Они нужны для расположения данных.

---

## Разобранный пример

Чтобы загрузки через `movzx` имели однозначный контракт, объявим маленькие поля беззнаковыми:

```cpp
struct Item {
    unsigned char tag;
    int value;
    unsigned short flags;
    Item* next;
};
```

Для типичной IA-32-модели:

| Поле | Размер | Смещение | Объяснение |
|---|---:|---:|---|
| `tag` | 1 | 0 | первый байт |
| padding | 3 | 1..3 | подготовка `value` к границе 4 |
| `value` | 4 | 4 | выровненный `int` |
| `flags` | 2 | 8 | выровненный `unsigned short` |
| padding | 2 | 10..11 | подготовка указателя |
| `next` | 4 | 12 | указатель IA-32 |

```text
sizeof(Item) = 16
```

Если `eax` хранит `Item* p`:

```asm
movzx edx, byte [eax]     ; unsigned char p->tag -> unsigned/int value
mov ecx, [eax+4]          ; int p->value
movzx esi, word [eax+8]   ; unsigned short p->flags -> unsigned/int value
mov edi, [eax+12]         ; Item* p->next
```

Здесь `movzx` следует не из смещения и не из размера структуры. Он следует из беззнаковых типов `unsigned char` и `unsigned short`.

### Знаковый вариант

Если поля объявлены так:

```cpp
struct SignedItem {
    signed char tag;
    int value;
    short flags;
    SignedItem* next;
};
```

то при расширении до 32 бит нужны:

```asm
movsx edx, byte [eax]     ; signed char tag
movsx esi, word [eax+8]   ; short flags
```

Для отрицательных значений `movzx` изменил бы числовой смысл. Например, байт `FFh` стал бы `255`, а не `-1`.

### Почему в примере не используется plain `char`

Знаковость типа `char` без `signed` или `unsigned` зависит от реализации. Поэтому учебный пример, который должен однозначно выбрать `movsx` или `movzx`, обязан явно писать `signed char` либо `unsigned char`.

Размер и signedness — два независимых решения:

```text
byte/word/dword → сколько байтов прочитать;
signed/unsigned → как расширить прочитанные биты.
```

## Доступ через аргумент-указатель

Пусть функция получает `Item* p` первым аргументом:

```asm
mov eax, [ebp+8]      ; eax = p
mov edx, [eax+4]      ; edx = p->value
mov eax, [eax+12]     ; eax = p->next
```

Нельзя писать:

```asm
mov eax, [ebp+12]
```

и считать это полем `p`: `[ebp+12]` является вторым аргументом кадра, а не смещением внутри объекта.

## Массив структур

```cpp
Item a[10];
```

Если `sizeof(Item)=16`:

```text
&a[i] = base + 16*i
```

Доступ к `a[i].value`:

```text
base + 16*i + 4
```

NASM:

```asm
mov eax, ecx
shl eax, 4
mov edx, [items + eax + 4]
```

---

## Связный список

```cpp
struct Node {
    int value;
    Node* next;
};
```

Типичное расположение:

```text
offset 0 → value
offset 4 → next
```

Переход к следующему узлу:

```asm
; eax = current
mov edx, [eax]       ; current->value
mov eax, [eax+4]     ; current = current->next
```

В массиве следующий объект находится по арифметическому шагу. В связном списке адрес следующего узла читается из памяти.

---

## Что зависит от ABI

C++ не гарантирует универсальные числовые смещения для всех компиляторов и параметров сборки.

Расположение могут менять:

- другая архитектура и размер указателя;
- требования ABI;
- `#pragma pack` или атрибут упаковки;
- битовые поля;
- наследование и виртуальные методы.

Отдельно от ABI, знаковость plain `char` является свойством реализации языка. Её нельзя угадывать по одному смещению в листинге.

Поэтому формулируй:

```text
В принятой учебной IA-32-модели поле имеет такое смещение при заданных типах и выравниваниях.
```

а не:

```text
Стандарт C++ всегда требует это смещение и такой способ расширения.
```

## Практика

### 1. Вычисли расположение

```cpp
struct A {
    unsigned char c;
    short s;
    int x;
};
```

Используй выравнивания 1, 2 и 4.

<details>
<summary>Ответ</summary>

```text
c@0, padding@1, s@2, x@4, sizeof=8
```

</details>

### 2. Доступ к полю

`eax` хранит адрес `A`. Загрузи `x`.

<details>
<summary>Ответ</summary>

```asm
mov edx, [eax+4]
```

</details>

### 3. Расширение поля

Для структуры из задания 1 загрузи `c` и `s` как 32-битные значения.

<details>
<summary>Ответ</summary>

```asm
movzx edx, byte [eax]     ; c — unsigned char
movsx ecx, word [eax+2]   ; s — short
```

Размер адресного шага и способ расширения выбираются отдельно.

</details>

### 4. Массив структур

Если `sizeof(A)=8`, выведи адрес `a[i].x`.

<details>
<summary>Ответ</summary>

```text
base + 8*i + 4
```

</details>

### 5. Найди ошибку signedness

```cpp
struct B { short value; };
```

```asm
movzx eax, word [edx]
```

Что неверно для `value=-1`?

<details>
<summary>Ответ</summary>

`movzx` даст `65535`. Для сохранения значения знакового `short` нужен `movsx eax,word [edx]`, который даст `-1`.

</details>

### 6. Найди ошибку списка

```asm
; eax = Node*
add eax, 8
; автор считает, что перешёл к next
```

<details>
<summary>Ответ</summary>

Для связного списка адрес следующего узла нужно загрузить из поля, например `mov eax,[eax+4]`. Арифметический шаг относится к соседнему элементу массива, а не к произвольному узлу списка.

</details>

## Типовые ошибки

| Ошибка | Почему неверно |
|---|---|
| сложить только размеры полей | игнорируются заполняющие байты |
| считать padding пользовательскими данными | это служебное место расположения |
| выбирать `movzx` только потому, что поле маленькое | signedness не определяется размером |
| считать plain `char` всегда signed или всегда unsigned | его знаковость зависит от реализации |
| спутать `[ebp+8]` и `[p+8]` | первое относится к кадру, второе — к объекту |
| переходить по списку арифметическим шагом | следующий адрес хранится в поле-указателе |
| считать типичное расположение требованием C++ | смещения зависят от ABI и упаковки |
| требовать знания структур без повторения | внешний пробел остаётся скрытым |
