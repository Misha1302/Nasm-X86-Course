# Пошаговые разборы сложных задач переноса

Эта страница не заменяет самостоятельную попытку. Открывай нужный раздел только после:

1. законченной попытки;
2. чтения краткого диагностического ключа;
3. невозможности найти первую строку расхождения самостоятельно.

Сначала раскрой только «направляющий вопрос». Полное решение используй последним.

<a id="tr-05"></a>
## TR-05: два объекта, а не сумма смещений

### Направляющий вопрос

После чтения `c->head` получено значение поля или адрес другого объекта?

### Граф данных

```text
argument c ──load [c+8]──> head pointer ──load [head+4]──> value
```

Сначала подпиши каждую стрелку как вычисление адреса или чтение памяти. Только после этого сверяй последовательность инструкций в [ключе](/transfer_keys#key-tr-05).

### Контрпример копированию

Размести `Container` и объект head в несмежных областях памяти. Тогда `[c+12]` и `[head+4]` гарантированно обращаются к разным адресам.

<a id="tr-16"></a>
## TR-16: три независимые области стека

### Направляющий вопрос

Какие байты принадлежат долгоживущему scratch, какие — аргументам текущего вызова, а какие — временному padding?

Нарисуй состояние до подготовки, после padding, после трёх `push` и после cleanup. Не включай 12 байт scratch в cleanup вызова: они были живы до вызова и остаются живы после него.

### Проверка

В каждой строке вычисли `esp mod 16`. Сравни результат со [зеркальным ключом](/transfer_keys#key-tr-16) только после собственной таблицы.

<a id="tr-13"></a>
## TR-13: `continue`, `break` и шаг цикла

### Направляющий вопрос

Куда должен вести `continue` в цикле `for`: сразу к проверке или сначала к изменению счётчика?

### Эталонная форма управления

Исходный код:

```cpp
for (int i=0; i<n; ++i) {
    if (a[i] < 0) continue;
    if (a[i] == 0) break;
    sum += a[i];
}
```

Блоки:

```text
init → check → load → negative?
                  ├─ yes → step
                  └─ no  → zero?
                            ├─ yes → end
                            └─ no  → add → step
step → check
```

Один из вариантов NASM:

```asm
xor ecx, ecx              ; i = 0

.check:
    cmp ecx, [n]
    jae .end

    mov eax, [a + 4*ecx]
    test eax, eax
    js .step               ; continue
    jz .end                ; break

    add [sum], eax

.step:
    inc ecx
    jmp .check

.end:
```

### Где обычно появляется первая ошибка

Если отрицательный первый элемент приводит к бесконечному циклу, проверь путь `continue`: счётчик обязан пройти через `.step`.

### Новый вариант

Измени условие: пропускать чётные элементы, завершаться на отрицательном, остальные прибавлять.

## TR-17: CFG и callee-saved на каждом выходе

### Направляющий вопрос

Какие рёбра CFG достигают `ret`, и проходит ли каждое из них через восстановление `esi`?

Сначала нарисуй блоки:

```text
prologue → sum → compare ──<= limit──> return
                          └─> clamp ──> return
return → restore esi → restore frame → ret
```

Затем проверь не наличие строки `push esi`, а доминирование и post-dominating восстановления относительно всех возвратов. Полный допустимый каркас находится в [ключе](/transfer_keys#key-tr-17).

### Mutation counterexample

Добавь `ret` в ветку clamp до общего эпилога. Семантическая проверка callee-saved должна отвергнуть такой вариант.

<a id="tr-19"></a>
## TR-19: layout раньше адресации

### Направляющий вопрос

Какой stride имеет `Item`, и на каком смещении внутри элемента находится `p.y`?

Составь таблицу `поле / offset / size / alignment`, затем отдельно выведи:

```text
address = base + i*sizeof(Item) + offsetof(Item,p.y)
```

Только после получения `12*i+6` выбирай инструкции и знак расширения. Сверка: [ключ TR-19](/transfer_keys#key-tr-19).

<a id="tr-23"></a>
## TR-23: план дерева до x87-инструкций

### Направляющий вопрос

В каком порядке вычислить три бинарных поддерева, чтобы не потерять операнды и не превысить нужную глубину?

Разбей выражение:

```text
left  = a+b
right = c-d
num   = left*right
den   = e+f
result = num/den
```

Для каждой инструкции выписывай весь `st(0..)` и глубину. Направление `fsubp` и `fdivp` проверяй числовым oracle, а не по внешнему виду мнемоники. После собственной трассировки сравни с [ключом](/transfer_keys#key-tr-23).

### Нижняя граница глубины

Объясни, почему при сохранённом результате одного поддерева вычисление другого бинарного поддерева требует ещё двух элементов, то есть максимум меньше 3 невозможен для этой прямой стратегии.
