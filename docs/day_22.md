## Зачем этот день

С целыми числами всё было относительно честно:

```text
32 бита -> одно из 2^32 возможных значений
```

Да, знаковая и беззнаковая интерпретации могут читать эти биты по-разному, но сами целые значения в допустимом диапазоне представлены точно.

С вещественными числами иначе. Многие привычные десятичные дроби нельзя точно записать конечным числом двоичных битов.

Например:

```cpp
double x = 0.1;
```

обычно хранит не ровно `0.1`, а ближайшее представимое значение.

Сегодня разбираем, почему так происходит и как в общих чертах устроены числа с плавающей точкой.

---

## Главная мысль

Число с плавающей точкой хранится приближённо в форме:

```text
sign * mantissa * 2^exponent
```

У числа есть:

- знак;
- порядок;
- значащая дробная часть;
- специальные случаи: нули, денормалы, бесконечности, NaN.

Центральный инвариант для сравнения:

> Допустимая ошибка задаётся смыслом задачи; машинный тип сам не выбирает универсальную `eps`.

---

## 1. Двоичные дроби

В десятичной системе:

```text
123.45 = 1*100 + 2*10 + 3*1 + 4/10 + 5/100
```

В двоичной системе дробная часть использует степени 2:

```text
0.1₂ = 1/2
0.01₂ = 1/4
0.001₂ = 1/8
```

Пример:

```text
5.75 decimal
```

Целая часть:

```text
5 = 101₂
```

Дробная часть:

```text
0.75 = 1/2 + 1/4 = 0.11₂
```

Итого:

```text
5.75₁₀ = 101.11₂
```

---

## 2. Почему `0.1` не точное

`0.1` в десятичной системе — это:

```text
1/10
```

А:

```text
10 = 2 * 5
```

Конечные двоичные дроби имеют знаменатель степени двойки:

```text
1/2, 1/4, 1/8, 1/16, ...
```

Если в знаменателе есть множитель 5, двоичная дробь обычно становится бесконечной периодической.

```text
0.1₁₀ = 0.00011001100110011...₂
```

Поэтому компьютер хранит ближайшее число, которое помещается в доступные биты.

---

## 3. Почему это важно

В C++:

```cpp
double a = 0.1;
double b = 0.2;
double c = 0.3;
```

Не стоит без доказательства писать:

```cpp
if (a + b == c)
```

Потому что `a`, `b`, `c` могут быть приближениями.

### Абсолютная погрешность

Для чисел около нуля или заранее ограниченного масштаба может подходить:

```cpp
std::abs(x - y) <= absoluteEpsilon
```

Но одна фиксированная абсолютная граница не универсальна. Ошибка `1e-9` может быть огромной для результата порядка `1e-12` и несущественной для результата порядка `1e12`.

### Относительная погрешность

Для ненулевых значений разных масштабов полезно сравнивать ошибку с величиной самих чисел:

```cpp
std::abs(x - y) <= relativeEpsilon * std::max(std::abs(x), std::abs(y))
```

Но только относительный критерий неудобен около нуля, где масштаб тоже стремится к нулю.

### Комбинированный критерий

Обычная общая форма:

```cpp
std::abs(x - y) <= std::max(
    absoluteEpsilon,
    relativeEpsilon * std::max(std::abs(x), std::abs(y))
)
```

Здесь:

- `absoluteEpsilon` задаёт допустимую ошибку около нуля;
- `relativeEpsilon` задаёт допустимую долю ошибки для больших значений.

Конкретные числа нельзя выбирать «по привычке». Они зависят от единиц измерения, диапазона входов, числа операций и требований задачи.

### Когда точное равенство допустимо

`==` не запрещено всегда. Оно может быть правильным, когда:

- проверяются специальные точно заданные значения, например результат присваивания того же объекта;
- алгоритм работает только с целыми значениями, точно представимыми в выбранном формате;
- сравниваются битовые представления намеренно;
- контракт задачи прямо требует точного совпадения.

Ошибка — не сам оператор `==`, а использование его без доказательства нужного контракта.

Ассемблер не добавляет точности: процессор выполняет операции только над представимыми значениями с плавающей точкой.

---

## 4. Общая идея научной записи

В десятичной записи:

```text
12345 = 1.2345 * 10^4
```

Для двоичных чисел с плавающей точкой идея та же:

```text
value = mantissa * 2^exponent
```

Например:

```text
101.11₂ = 1.0111₂ * 2^2
```

Потому что мы перенесли точку на 2 позиции влево.

---

## 5. Устройство `float`

Обычный 32-битный `float` можно представить так:

```text
31     30          23 22                    0
+--------+------------+----------------------+
| sign   | exponent   | fraction             |
+--------+------------+----------------------+
  1 bit     8 bits           23 bits
```

| Поле | Зачем |
|---|---|
| `sign` | знак числа |
| `exponent` | порядок, степень двойки со смещением |
| `fraction` | дробная часть мантиссы |

Упрощённая формула:

```text
(-1)^sign * mantissa * 2^exponent
```

Точная формула IEEE использует смещение порядка и скрытую единицу для нормализованных чисел. На первом проходе важна идея: число хранится как знак, масштаб и значащие биты, а не как десятичная строка.

---

## 6. Нормализованные числа

Для обычных нормализованных чисел мантисса имеет вид:

```text
1.xxxxx₂
```

Эта первая `1` обычно не хранится явно. Её называют скрытой старшей единицей.

Почему можно не хранить?

Потому что у нормализованного ненулевого двоичного числа первая значащая цифра всегда `1`.

Пример:

```text
101.11₂ = 1.0111₂ * 2^2
```

Мантисса начинается с `1.`.

---

## 7. Денормализованные числа

Денормализованные числа нужны для очень маленьких значений около нуля.

Идея:

```text
когда нормализованного exponent уже не хватает,
мы разрешаем числа без скрытой ведущей 1.
```

Они помогают сделать переход к нулю более плавным.

Для курса достаточно понимать:

- нормализованные — обычные числа;
- денормализованные — очень маленькие числа около нуля;
- для них используется отдельная кодировка.

---

## 8. Специальные значения

Формат с плавающей точкой хранит не только обычные числа.

| Порядок | Дробная часть | Смысл |
|---|---|---|
| все биты 0 | 0 | `+0` / `-0` |
| все биты 0 | не 0 | денормализованное число |
| обычный порядок | любое | нормализованное число |
| все биты 1 | 0 | `+Inf` / `-Inf` |
| все биты 1 | не 0 | `NaN` |

### `+0` и `-0`

У чисел с плавающей точкой есть положительный и отрицательный ноль.

Обычно они сравниваются как равные, но в некоторых операциях знак нуля может проявляться.

### Бесконечность

`Inf` появляется, например, при переполнении или делении ненулевого числа на ноль в модели с плавающей точкой.

### NaN

`NaN` означает «не число».

Это не “очень большое число”. Это специальное значение для некорректных результатов:

```text
0.0 / 0.0
sqrt(-1.0) в вещественной арифметике
Inf - Inf
```

---

## 9. Неупорядоченные сравнения с NaN

NaN не ведёт себя как обычная числовая константа. В модели IEEE сравнение с NaN считается **неупорядоченным**:

```text
NaN == NaN  -> false
NaN <  x    -> false
NaN >  x    -> false
NaN != NaN  -> true
```

Поэтому такая проверка неверна:

```cpp
if (x == NAN) { ... }
```

Используют `std::isnan(x)` или низкоуровневую проверку признака неупорядоченности, когда изучены соответствующие флаги.

Минимальный контрпример:

```cpp
double x = std::numeric_limits<double>::quiet_NaN();
assert(x != x);
```

Это специальное правило NaN, а не обычная потеря точности.

Комбинированная проверка близости также не заменяет `isnan`: если один операнд NaN, сначала нужно обработать этот специальный случай по контракту программы.

## 10. Округление

Так как битов конечное число, результат операции часто приходится округлять.

Например, если точный результат требует больше битов мантиссы, чем есть, процессор выбирает ближайшее представимое значение по текущему режиму округления.

Типовая мысль:

```text
floating point arithmetic is not real-number arithmetic
```

Она похожа на вещественную математику, но не равна ей идеально.

---

## 11. Почему порядок операций важен

В вещественной математике:

```text
(a + b) + c = a + (b + c)
```

Для чисел с плавающей точкой равенство может нарушаться из-за округления.

Примерная идея:

```cpp
double a = 1e20;
double b = -1e20;
double c = 3.14;
```

```cpp
(a + b) + c = 3.14
```

а:

```cpp
a + (b + c)
```

может потерять `c` при сложении очень большого и маленького числа.

Для ассемблера это важно: порядок операций может влиять на точность.

## Практика

#### 1. Представь `5.75` в двоичной системе

<details>
<summary>Ответ</summary>

```text
5 = 101₂
0.75 = 0.11₂
5.75 = 101.11₂
```

</details>

#### 2. Почему `1/10` бесконечна в двоичной системе?

<details>
<summary>Ответ</summary>

Потому что `10 = 2*5`, а конечные двоичные дроби имеют знаменатель степени 2. Множитель 5 даёт бесконечную периодическую запись.

</details>

#### 3. Что означает: все биты порядка равны 1, а дробная часть равна 0?

<details>
<summary>Ответ</summary>

Бесконечность: `+Inf` или `-Inf` в зависимости от знака.

</details>

#### 4. Почему NaN — не “очень большое число”?

<details>
<summary>Ответ</summary>

Потому что NaN означает «не число» — специальный результат некорректной операции.

</details>

#### 5. Почему одной абсолютной `eps` недостаточно для всех задач?

<details>
<summary>Ответ</summary>

Одинаковая абсолютная ошибка имеет разный смысл для чисел порядка `1e-12` и `1e12`. Нужны границы, соответствующие масштабу и контракту задачи; часто объединяют абсолютный и относительный критерии.

</details>

#### 6. Запиши комбинированный критерий

<details>
<summary>Ответ</summary>

```cpp
std::abs(x - y) <= std::max(
    absoluteEpsilon,
    relativeEpsilon * std::max(std::abs(x), std::abs(y))
)
```

Перед ним отдельно обрабатывают NaN и, при необходимости, бесконечности.

</details>

#### 7. Когда `==` может быть обоснован?

<details>
<summary>Ответ</summary>

Например, при намеренном сравнении точно представимых значений или битовых состояний, если это следует из контракта алгоритма. Запрещён не оператор, а необоснованное предположение о точности.

</details>

#### 8. Почему `x == NaN` не проверяет NaN?

<details>
<summary>Ответ</summary>

Потому что сравнение с NaN неупорядочено, и NaN не равен даже самому себе. Нужна `isnan` или проверка признака неупорядоченности.

</details>

## 13. Типовые ошибки

| Ошибка | Почему плохо |
|---|---|
| думать, что `0.1` хранится точно | в двоичной системе это бесконечная дробь |
| сравнивать float/double через `==` без контракта | округление может дать неожиданный результат |
| использовать одну абсолютную `eps` для любых масштабов | допустимая относительная ошибка меняется вместе с величиной чисел |
| использовать только относительную ошибку около нуля | масштаб стремится к нулю и критерий становится слишком строгим |
| выбирать `eps` без единиц измерения и требований задачи | порог не имеет доказанного смысла |
| считать NaN большим числом | NaN — не число |
| пропускать отдельную обработку NaN | обычная проверка близости не задаёт нужную семантику NaN |
| забывать про `Inf` | переполнение может дать специальное значение |
| думать, что порядок операций не важен | операции с плавающей точкой не полностью ассоциативны |
| путать нормализованные и денормализованные числа | денормализованные числа описывают особую область около нуля |
